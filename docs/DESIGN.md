# Design

How SkyrimCoop is meant to work, and why. This is a skeleton: the decisions that are made, the parts that exist, and for everything else a heading that says what has to be decided there. A section is filled in when its phase of [PLAN.md](PLAN.md) is built and tested, with what the game turned out to do, not before.

Nothing here has been run in a game yet.

## The idea

A small group of friends plays through Skyrim together in one world.

- **One host, whose save is the world.** The host loads their own save and plays. Friends join it. Quests, the state of the world, the time of day: the host's game decides, and the host's save keeps it.
- **Friends follow.** A friend plays their own character, with their own gear and skills, kept in their own save. Their save keeps the character, not the world: what the group did lives in the host's save.
- **Steam first.** The host's game opens a friends-only Steam lobby. A friend joins from the Steam overlay or the friends list. The games talk through Steam's relay network: no server to rent, no port to open, no address to pass around.
- **By address second.** A direct UDP connection to an address and port (a LAN, a forwarded port, a VPN of the group's own choosing), and a dedicated server for those who want one. The same session either way.
- **Tested for hours before it ships.** A release is a release candidate that two scripted games played for a long session without a failure ([RELEASING.md](RELEASING.md)).

It is the design of [F4Multiplayer](https://github.com/Jolley71717/F4Multiplayer), the sister project for Fallout 4, moved to another game by the same engine family. Where that project has an answer that does not depend on the game, this one starts from it.

## Decisions made

| Decision | Why |
| --- | --- |
| The game is Skyrim Special Edition on Steam, the current version (the Anniversary Edition update line). Not the 2011 game, not Skyrim VR, not the GOG or Microsoft Store versions, for now. | One game version to reverse-engineer and test. Steam is how players join, so a version without Steam has no way in. |
| The plugin is an SKSE64 plugin built on CommonLibSSE-NG, finding the game's functions through the Address Library. | The same stack as the sister project's (F4SE, CommonLibF4, Address Library), so the same habits apply. Address Library ids survive most game updates. |
| The host owns the world; friends follow. | One source of truth. Two games that both decide drift apart, and no save can hold two worlds. |
| Steam lobbies, invites and the relay first; join by address second. | The reason for the project: joining should be an invite, not network administration. |
| Steam is reached through the game's own Steam library, by hand-declared functions found at run time. The Steamworks SDK is never in the repository and no Steam library ships with the mod. | The SDK's terms do not fit a GPL repository, and the game already has Steam loaded under its own app id. |
| GPL-3.0-or-later with the modding and linking exceptions, as F4Multiplayer. | The same license lets code move between the two projects, and CommonLibSSE-NG's license asks for it. |
| No code from other multiplayer mods. | Their licenses differ and some allow nothing ([PRIOR-ART.md](PRIOR-ART.md)); whether to build on any of them is the maintainer's decision, not a contributor's. |
| Game-free code is kept apart (`common/`) and unit-tested on every pull request; anything that touches the game is tested on two real games. | The split the sister project relies on: most protocol bugs are found without a game, and no game behaviour is taken on trust. |
| A release candidate first, then a long two-game test of exactly that build, then the release. | What is tested is what ships. |
| Logs name no person and no machine. | A bug report's log is attached in public. |

## What exists today

```
        game A (host)                                   game B (friend)
  +--------------------------+                   +--------------------------+
  | SkyrimCoop.dll           |                   | SkyrimCoop.dll           |
  |  src/main.cpp  start-up  |                   |                          |
  |  src/game/*  stand-ins   |                   |  src/game/*  stand-ins   |
  |  src/net/NetClient ------+--- transport -----+-- src/net/NetClient      |
  |  common/Server (thread)  |   Steam relay or  |                          |
  |  src/steam/*             |   UDP (ENet)      |  src/steam/*             |
  +--------------------------+                   +--------------------------+
```

- **Start-up** (`src/main.cpp`): keeps the last three logs, starts the log, checks the game's version (`src/RuntimeSupport.h`), reports how the game was started (`src/LaunchReport.h`, `src/Platform.cpp`), reads the ini (`src/Settings.h`, `src/Config.cpp`), and listens for SKSE's messages: data loaded, before and after a load, new game, save, delete. Its co-save ("SKCO") holds one record: the stand-ins taken out of the world for that save (below, "Nothing of the session in a save").
- **The protocol** (`common/Protocol.h`): a first, small one. A hello with the mod's protocol version, the player's name, a password and the load order; a welcome or a refusal with its reason; the session's plugin table (each plugin a place, sent to every game as it grows); players joining and leaving; each player's state (cell or worldspace, position, heading, speed, a few flags, the sender's clock); each player's looks (race, sex, weight and the armor worn, as form ids), which the server keeps and gives to whoever joins later; a heartbeat. Two channels: reliable, and unreliable-sequenced for state.
- **The server** (`common/Server.cpp`): lets players in (same protocol version, the right password, room left; any load order whose plugin list it has), gives each an id, keeps the session's plugin table, and passes each player's state and looks to the others. It runs as a thread inside the host's game, or alone as `SkyrimCoopServer.exe`.
- **Transports** (`common/Transport.h`): the session does not know how bytes travel. `common/EnetTransport` is UDP through ENet; `src/steam/SteamTransport` is Steam's relay messaging; `tests/FakeTransport.h` is memory, for tests.
- **Steam** (`src/steam/`): the lobby, invites, "Join Game", friends who are hosting, carried from the sister project. Not yet shown to work under Skyrim ([GETTING-STARTED.md](GETTING-STARTED.md), "The first thing to test").
- **The session in the game** (`src/net/Session`): hosting runs the server in the game, reached by friends through Steam and by the host's own connection over UDP on this machine only; a friend joins from Steam itself (an invite, "Join Game", a `steam://joinlobby` address, or the lobby on the command line Steam starts the game with, `src/net/LaunchArgs.h`). Once in, each game sends its player's state 20 times a second and its looks when they change.
- **The game side** (`src/game/`): the load order (`LoadOrder`), the local player (`LocalPlayer`), the other players' stand-ins (`RemotePlayers`, with `StateBuffer` and `Gait`), the frame (`GameThread`, still the stand-in tick) and, for the rig, a virtual gamepad (`VirtualPad`) and console commands (`Console`). [PORTING.md](PORTING.md) has a section for each.
- **Privacy** (`common/Redact.h`): players are `player N` in every log line; addresses are masked; a last scrub runs over every line.

## Sessions

Carried from the sister project and unit-tested:

- A friend is let in only with the same protocol version and the host's password. Each refusal has its own reason, shown to the player.
- Load orders may differ (since protocol 4): other mods, or the same ones in another order. Only a hello without a plugin list (a tool's, or a load order too long for a hello) must have the session's load order, since nothing can translate its forms. The first player in the session sets the session's load order; on a hosted game that is the host.
- Each game has a random identity kept on its PC; a player who drops and returns gets the same player id. It is not a Steam id and says nothing about the person.
- Up to 8 players by protocol, 4 by default.

To design when phase 1 is built: what a friend sees while joining, joining in the middle of a fight or a scene, the host leaving, a friend's game crashing, bans.

## Form ids across load orders

Every object in the game is named by a form id whose first byte (or, for light plugins, bits) depends on the load order. Two games with other mods, or the same mods in another order, give the same object other ids. So no game's ids go over the wire (protocol 4, the sister project's design):

- **The session's plugin table** (`Protocol::PluginTable`): the first player's load order, with the plugins each later joiner brings added after the rest of their kind (`FormIds::Extend`), so an id it gave never changes. The server sends it to each joiner before the welcome, and to everyone in whenever it grows, on the reliable channel.
- **A form on the wire** is its plugin's place in that table and its number within the plugin: a plugin is named by its file name, never by where any game loads it.
- **Each game translates at its edge** (`common/FormTranslate.h`): every packet out from its own ids to the session's, every packet in from the session's to its own, by plugin name (`FormIds::Mapper`), before anything reads it. The rest of the game only ever sees its own ids, the server only the session's. With the same plugins in the same places (the usual case) no id changes.
- **A runtime form (FF) is never sent as a form.** A game makes them as it runs (a brewed potion, a form a mod's script or SKSE plugin creates), so the id names nothing in another game, or that game's own runtime form of the same number. A sender sends the plugin form it was made from instead where there is one (an armor's template, `FormIds::Shareable`); the edge skips any runtime id left in a message, both ways, whatever the load orders (the identity too); and a receiver never looks one up (`RemotePlayers::Dress`, the race). An item's own enchantment (a player-made one is a runtime form in the item's extra data) is not carried yet.
- **A form of a plugin the other game lacks is skipped, never guessed**, and the message still goes: a place (a state's cell and worldspace, as a pair) becomes "nowhere this game has" (both 0), so no stand-in is shown in the wrong world; a worn item is left out; a race becomes none, and the stand-in is a Nord. Each such plugin is named once in that game's log. A plugin full in one game and light in the other maps too, but for its forms past the 4096 a light plugin can number.
- The server's log says only how a joiner's load order differs (counts); each game's own log names the plugins.
- On the rig: the `forms` developer command (`src/net/FormsCommand.h`) reads a game's edge, and finds a form by plugin file name and number; `tools/rig/steps/forms.sh` (the harness's step `forms`, run only when named) puts two plugins of the VM's game in another order and checks gear crosses both ways, on the stand-in actor itself (`standins` lists its `equippedIds`).

To decide later: a host option to refuse friends whose mods differ (the sister project lets the host ignore some plugins in the comparison; it would also stop a friend who is let in from filling the session's plugin table with made-up names, which only grows until everyone leaves), and telling a friend in the game which plugins differ (the sister project's ModDiff, with the menu).

## The frame

Everything that reads or changes the game happens on the game's main thread, once per frame; network threads only queue. The stand-ins' movement does not wait for the tick: they are placed inside their own actor update, which the game runs every frame. SKSE offers no "every frame" call, so the plugin needs a hook in the game's main update. Not written yet ([PORTING.md](PORTING.md), "The frame"). Until it is, a stand-in tick serves the first test: a small thread asks SKSE's task queue every 16 ms to run the plugin's tick once on the main thread, one request at a time. It is not tied to the game's frames and may not run in every game state; it is replaced, not built on.

## Players

The first stand-in (`src/game/RemotePlayers`), kept simple on purpose:

- **What it is**: a plain NPC of the friend's race and sex, wearing the armor they wear and named as they are. Its base is one of the game's own character-creation presets of that race and sex (the lowest form id, so every game picks the same), an NPC of the load order; or, once its friend's face has come, a copy of that preset made at run time with the face on it (below). Either way the save sees only the preset (see "Nothing of the session in a save").
- **How it is moved**: the game never runs its AI. Every Character's actor update goes through one hook (the class's vtable, `Actor::Update`); for a stand-in it places the actor where its friend was 120 ms ago (blended between the two states either side, `StateBuffer`), turns it, runs the engine's no-AI update and tells its animation graph what its friend's legs do (`Gait`: the graph's Speed and Direction, and its move, sprint, sneak and jump events). Any other actor gets the game's own update.
- **Its legs**: the engine does not keep a Speed or Direction set on an actor's graph. Each time the graph updates it pulls both through a channel per variable (`BSTAnimationGraphDataChannel<Actor, float, ActorSpeedChannel>` and `<..., ActorDirectionChannel>`) from the movement speed and direction in the actor's process, and the actor's movement job sets those every frame from its movement controller's desired movement: none, for an actor whose AI never runs. So a stand-in's graph read 0 and it slid along with its legs still. The two channels' polls are hooked (their vtables, by Address Library id): after the engine's poll, a stand-in's channel holds its friend's Speed and Direction, as its own update last wrote them (`GaitDrive`; values not written for half a second go back to the engine's). The movement controller is left alone, so nothing moves the stand-in but its friend's states.
- **When it is there**: while both players are in the same interior cell or the same worldspace and within about two cells of each other.
- **What its hands do** (`src/game/PlayerActions`, `src/game/StandInRules.h`; written in protocol 9, not run in a game yet; the rig step `actions` is ready for it): each game hears its own player's animation-graph events (the player's `NotifyAnimationGraph`, hooked through the player's own vtable) and sends the ones a stand-in should replay (draw and sheathe, swings and power attacks, block and bash, bow draw and release, casting in either hand, shouts; never the legs' events, which `Gait` already drives) as player actions, batched, with the sender's clock. The server stamps the sender's id and passes them on with a budget per player (it says once when it drops some). The other game queues them and plays each on the stand-in's graph when its time comes, 120 ms behind, like the states; what the graph refuses is counted by kind.
- **What it holds**: a player's looks now carry the right hand, the left hand, the quiver and the voice (shout or power), form ids mapped like the armor; one the other game's load order lacks is marked missing, never guessed. The stand-in is dressed in them (in a hand only playable weapons, conjured ones (a bound weapon is non-playable, and a player only has one from its spell), spells, scrolls, torches and playable armor; in the quiver playable ammo, or any while a conjured weapon is in a hand; for the voice a shout or a power), checked each second, dressed again (no sooner than 5 s after the last time) when what it holds or has ready drifts, and its quiver topped up. A power is taught to the stand-in itself; a shout is only readied, never taught, since an actor that is not the player keeps its shouts in its base, a load-order preset that a save would keep changed (the rig compares the base's shouts, `baseShouts=`). Copies of NPCs still get no spell in a hand (below, "Not shared yet"): the gear code they share with stand-ins leaves spells to the stand-ins. A hand's change re-dresses the same stand-in; another race, sex or weight makes a new one.
- **It deals nothing here**: its friend's blows and spells are settled by its friend's game, so a stand-in's attack damage is zero, it is essential, its health, magicka and stamina are kept full, its spells' effects on anyone here are refused (except its own effects on itself, `MagicKept`), and health its blow still takes from an NPC or our player is given back (the health-damage call of Character and of the player, hooked), all counted.
- **Draw and aim**: a stand-in whose drawn state still differs from its friend's 1.5 s after it should have followed is made to draw or put away its weapon directly (no more than once every 3 s); its friend's aim pitch, capped at 60 degrees, tilts it so bows and spells point where they point.
- **Its face** (`src/game/Face`, `src/game/FaceRules.h`; written in protocol 10, not run in a game yet; the rig step `faces` is ready for it): each game reads its own player's face once a second: the head parts, the hair colour (its form and its colour), the complexion, the skin, the height, the 19 face sliders and 4 preset parts, the tint layers (each named by its race's tint mask: its index and its texture's path, so a race a mod renumbered still finds the same mask; the skin tone's colour also becomes the body's tint) and sends it after every welcome and whenever it changed and held still for two reads (a slider dragged at a barber's sends where it stops), on a timer of its own. While a menu that edits faces is open (the race menu, which face editor mods open too, or any menu that pauses the game) nothing is sent; the face goes once, as it was left, when the menu closes. The server keeps the newest for those who join later and passes it on (a burst of four, then one a second, the newest owed past that). The forms are mapped like the looks: a head part the other game lacks is left out, and the stand-in keeps its preset's of that kind (it never shows no eyes); a colour form it lacks reads none and the colour itself is used; a complexion or skin it lacks is the preset's. A face goes on only when it is for the stand-in's preset's race and sex. The stand-in then stands on a copy of its preset (`CreateDuplicateForm`), its head built by the engine from the copy's parts at run time as it does for the player and the presets themselves (the copy keeps the preset flag; no engine patch). Each copy holds one face at a time. The same friend's same face (and weight) is placed again on the copy that holds it; a changed face places a new stand-in, no sooner than 2 s after the last, and is written into a copy of the same preset that no actor stands on any more (none here, none on its way out whose 3D may still be built from it), so the copies made follow how many stand-ins show a face at once, not how often faces change. Only when every copy of that preset is in use is one more made, at most 64 in a game run (the game never frees a form made at run time), after which friends get their preset's face; none made before a load is placed or written into after it (a load may free them). As the sister project learned, a head built at run time can fail to appear: a stand-in on a copy whose 3D shows no face node for 3 s is built again once, and with still none 3 s later its friend's face is given up for the session (the preset's from then on); our own player's face node gone for 2 s while one stands there gives that face up too, and ours is asked back once if it is still gone 2 s later. Our own face node is read from the third-person 3D, and only while it can have one at all: in the race it last had one in (not a werewolf's or a vampire lord's form, which have none; the sister project skipped power armor the same way), not in first person, and not while a face editor is open; ours is never built again in those. Before a save, a stand-in on a copy gets its preset back as its base, and the co-save names the preset; one still loading its 3D then is counted and logged (its head may be half built from the copy). The dev command `faces` says ours (read, its hash and session hash, what was sent, first person, the runtime preset NPCs this game did not make) and each stand-in's (the face that came, whether it goes on, the copy it stands on, whether it has a head, what its built head shows read from its 3D, and how much of the face that copy holds against what came); `faces nudge [undo]` changes our face for the rig.
- **Seeing it**: the dev command `actions` says what was sent and, for each stand-in, what came, what played or was refused, what it holds against what it should, and what it did and was given back (its friend's spells refused, blows and casts, health taken and given back); our part says what the game shows our player doing (attack, block, cast and shout states, stamina and magicka spent: the rig's proof that a press did something), what it holds and its health; `actions equip <right|left|ammo|voice> <id>` equips our own player for the rig and says whether it took.
- **In water** (`src/game/Water`, `src/game/WaterRules.h`, `Gait`; written in protocol 11, not run in a game yet; the rig step `swim` is ready for it): a state says whether its player or NPC swims (the actor state's swimming bit) and, since protocol 11, whether it swims with its head under water (the engine's underwater flag, or nine tenths of it under). A stand-in or a copy of one that swims is shown swimming: its graph is told `SwimStart` and `SwimStop` (the swim event goes first, and the walk and sprint are started again in the water's mode), its actor state's movement bits match, under water it is pitched as its friend looks, held to 75 degrees (a player swims where they look), and at the surface it is level. A copy's pitch is set every frame, level in every state but flying and diving, so a copy taken out of the water from under it (a script moves it, its runner's states held and came again on the shore), or a dragon that lands, keeps no old pitch. Its height is its friend's: the engine's own update, run after it is placed, floats a swimmer to the surface, so one it moved more than 8 units off is placed back (counted). An actor whose race does not walk (a fish) is never told to swim: its graph is always in the water. A graph event the graph turns away is now sent again alone the next frame, not with the frame's others; a swim event turned away three times for one change is given up until the next (a graph with no swim state keeps walking), and a copy's walk events are still asked once. The dev command `swim` says ours (swimming, under, how deep, the character controller's state, how often each changed and the graph events our player took around each change, the names the stand-ins are sent are checked against), each stand-in's and the copies' (shown swimming, the swim events taken, refused and given up, its height against its friend's, its pitch); `swim find [radius]` finds the nearest water deep enough to swim in all round, for the rig. The rig step `swim` judges by what the engine decided, not only by what the plugin set: the stand-in's character controller in its swimming state (or the engine's own swimming flag), how often the engine's update moved it off its depth while it rests (a controller that never swims would be pulled off and put back each frame, a jitter), and its body as drawn (the line from its 3D's pelvis to its head), which must tip down as it dives when its friend's does. It checks NPC copies too: a person and a creature the mover's game runs are moved into the water with the console, and their copies in the other game must swim the same way (shown, the engine's state, the swim events taken and none given up, no jitter); a fish's copy must be told no swim event. Whether the swim graph draws a stand-in's dive from its angle at all is the open question the body check answers on the rig.
- Open, to see on the rig: whether a copy of a preset builds its head at run time as the presets do (the design assumes so: the preset flag is the engine's "build this head from its parts" case), whether a head built at run time draws the copy's tint layers (skin tone, paint), and whether `CreateDuplicateForm` copies an NPC whole. Not carried: RaceMenu's body morphs, overlays and node transforms.
- **Riding** (`src/game/Riding`, `src/game/RideRules.h`, `common/RideBook.h`; written in protocol 12, not run in a game yet; the rig step `ride` is ready for it): who rides what is said apart from the states (message 55, `kRides`): each game says its own player's ride and the rides of the NPCs it runs, as each begins, changes mount or ends, naming the mount as the session names an NPC (a load-order horse by its reference, a horse made as the game ran by its spawner). The server passes on a player's ride only from that player's game and an NPC's only from its runner's, each change once (the same ride from a new runner is a change: the book holds it as that game's, so the old runner's leave does not end it, and the old runner hears it too), keeps them for a joiner, and ends every ride a leaving player's game said; past a game's budget a change is owed, never dropped. A mount goes with its rider: a game asks for the horse its player or one of its NPCs sits on at the claim rate (as a follower), lets go of one another game's NPC rides, and a horse made as the game ran is shared as its spawn while its own ride it or it is its player's last horse. Every other game seats the actor that shows the rider (a friend's stand-in, a copy of the NPC) on the actor that shows the mount through the engine's own way onto a mount, in rounds: the mount activated by the rider (what pressing the button on a horse does), the console's `activate` two seconds later, both with the mount's activation opened for the try (a copy of another game's spawn is blocked from activation); three rounds five seconds apart, then given up (said in `ride`). The engine's quick put-on (`PutActorOnMountQuick`) is no way onto a mount: it takes no mount, and by its signature finishes the mount the rider's interaction already names (the `ExtraInteraction` that `GetMount` reads), so it is tried only on a seated rider the engine has on its mount but far from the saddle (not yet confirmed by reverse engineering; the rig's `quicks=` shows whether it is ever needed). One on another mount, or on one it should not be on, is got off (`StopInteractingQuick`). A seated rider is carried by the engine: the update hooks no longer place or turn it or tell its walk (its actions still play), and one more than 150 units from its mount for a second is first finished onto it (the quick put-on), then put back on it each second it stays far (the rig fails a ride that needed either). Getting on, getting off and riding are each graph's own events (any name starting `horse`, or holding `mount` or `dragonrid`): a friend's or a runner's are never played again on a stand-in or a copy. An actor of ours that leaves the world (a stand-in, a copy of a spawn, before a save too) gets off its mount, or its rider off it, first. A mount a game lacks reads as none: its rider is shown on foot. At a handover a game keeps a copy as it was for three seconds while the new runner says the ride again, and the new runner says it once whatever it shows: the same ride, or its end when it has the NPC on foot. Open, for the rig: whether an AI-less stand-in takes the activate path at all (F4Multiplayer's seat in furniture needed the console's), whether the engine carries a seated rider whose AI never runs (the step fails a ride in which the plugin had to put it back), whether the quick put-on ever finishes a seat, and dragons (the unit tests cover their rules).
- **Projectiles** (`src/game/Shots`, `src/game/ShotRules.h`; written in protocol 13, not run in a game yet; the rig step `shots` is ready for it): every projectile an actor launches is said once as it leaves (message 57, `kShots`) and launched in every other game from the actor that shows its shooter there. That covers the class, not a list of weapons: arrows and bolts, every spell's projectile whatever its kind (missile, lobbed rune, beam, flame stream, cone, barrier), dual casts, concentration streams, shouts, a staff's, and an NPC's or a creature's (a dragon's breath) as much as a player's. The update of the seven projectile classes is hooked (`Projectile::UpdateImpl` in each class's vtable). At a projectile's first update (never seen, younger than 0.1 s) one whose shooter is our player or an NPC this game runs is said: its record, its sources (weapon, ammunition, spell, an arrow's enchantment and poison), where it left, its angles, its power and scale, its hand and whether it was a dual cast or part of a held stream; a held stream is said at most once per 80 ms per shooter and hand, within a budget below the server's. The server passes on a player's own shots and those of the NPCs its game runs, the sender named, within a budget per game (past it dropped, said once in its log: a shot's flight is over before a budget would let it go). The forms are mapped like the looks: a shot whose record or NPC the reader lacks is left out, a source it lacks becomes none. A friend's shot is launched when the stand-in or copy is drawn at the moment it left (120 ms behind, like the states; one that waited a second is dropped), only when that actor is within 300 u of where it left (more for a big actor), from the shooter's own origin, with no auto-aim, no combat controller and no target; the engine may still aim a launch at whoever the actor looks at (the sister project saw a stand-in's missile go straight at the local player), so a launch more than a degree off its shooter's aim is turned back to it in its own first two updates, before and after the engine's update, inside the hook (on the thread that updates it: the tick runs on the game's job threads, and projectiles may update on others), and read once more after (what is left of the aim). What a stand-in's or a moved copy's own graph launches as it replays its friend's or runner's release or cast (a native) is ended before it moves: its updates are skipped for 2 s and it is killed meanwhile, and one still there and not ended after that is counted (`survived=`) and held 30 s more. This game's own launches are told apart by the projectile once the launch returns, and before that by their shooter, record and origin. A projectile is known by its object and its form id together: the game reuses a freed one's memory and may give its freed id to the next reference it makes, so either alone may name another projectile by the next frame. The tick ends a launch of ours only while no update of it runs: it claims it first, and an update that starts meanwhile is skipped. The hits the game reports of each launch of ours are counted (its first hit, on our player apart, and a hit again), so the rig tells a hit from a miss and one hit from two. What a launch hits is that game's business: a stand-in's harms no one (its attack damage is zero and its spells' effects are refused, above), a copy's deals what the local game runs, as its blows do. The launches a game made are ended once their flight is over (an arrow that stuck after 2 s, so no one picks up arrows that are not there; a rune after its record's life, at most 30 s; any other after 12 s), at most 64 fly at once, and all are ended before a save. The dev command `shots` says ours (seen, said by kind, NPCs', dual casts, coalesced, dropped), theirs (heard, launched by kind, late, too far, unknown, failed), the natives ended, our launches flying and how each ended, the hits, the aim before and after the fix, per game heard from; `shots find <kind>` finds a spell of that projectile kind (or a crossbow and bolts) for the rig; `shots last` the last said and launched; `shots strays [record]` the projectiles in the world whose shooter is missing or a stand-in, for the rig after a load. Open, for the rig: whether `Projectile::Launch` runs a projectile's first update before it returns (the hook tells our launches apart either way), whether a stand-in's replayed release launches a native at all, and whether a projectile ended for a save is gone from it. Not shared yet: where a projectile ends (a rune or an explosion goes off on its own in each game), arrows left in a hit NPC's inventory, and projectiles with no actor behind them (a trap's, a script's), which each game's world launches for itself.
- **Furniture** (`src/game/Furniture`, `src/game/SitRules.h`, `common/SitBook.h`; written in protocol 14, not run in a game yet; the rig step `sit` is ready for it): who sits, lies, leans or works in what is said apart from the states (message 58, `kSits`), for every kind of furniture (a chair, a bench, a bed or a bedroll, a lean spot, a crafting station, a work spot, a dragon's perch) and every actor a game shows (a friend's stand-in, a copy of any NPC: a person, a creature, a follower, a summon, a dragon). Each game says its own player's and those of the NPCs it runs as each gets in, changes furniture or gets up (getting up counts as up already, so the others rise as it starts), read from the actor's sit/sleep state and the furniture its AI process names: the reference (none for one made as the game ran), its record, where it stands, the marker used and its kind; a rider (its sit state is the saddle's) is never in furniture. The server keeps them in the riding book's rules (`RideBook::BookOf`): a player's only from that player's game, an NPC's only from its runner's, each change once, a joiner told all, a leaver's ended, past a budget owed. The forms are mapped like the rides: an NPC the reader lacks is left out, a reference or a record it lacks becomes none. Every other game finds its own copy of the furniture: the reference named when it has it (and it is of that record), else the nearest of that record within 48 u of where it stands there (a bedroll put down, a mod's), else none and the actor is shown standing by it (the reference named is looked up; one found by its record is kept while it is usable there, and the cell is walked for one at most once a second per actor); furniture its own player is in, at the same marker, is not given to the other (it waits beside it). The actor is put in through the engine's own way in, in rounds: the furniture activated by the actor, the console's `activate` two seconds later, three rounds five seconds apart, each once actor and furniture have had their 3D for a second; while the engine gets it in or up, the engine's own update runs for that actor (a stand-in's or a copy's AI never runs otherwise, and the sit procedure is the AI's), at most six seconds getting in (then it is taken out with `StopInteractingQuick` and the rounds go on) and three getting up. An actor in furniture, getting in or out, or near the furniture its friend is said to be in, is not placed or told its walk by the update hooks (its actions still play). Out of it (its friend got up, or it is in other furniture): the engine's own getting up first (its sit state set to want-to-stand or want-to-wake, written in the actor's own update on the thread that updates it, since the same word holds its life, knock and fly states), then at once if it is not up in three seconds. An actor on its way out of the world (a save, a leave, a load) is taken out first. Graph events an actor's graph takes while the engine has it in furniture are the engine's play: they are never sent, as every game plays its own. Not yet: a player in a bed (the game's sleep menu takes the player to sleep, not into the bed, and sleeping together is the menu's question), and which of several markers of a bench the other is put at (the engine chooses).
- Open, for later: guards, factions and crime; kill moves; transformed forms; whether a stand-in's arrows and spells, now harmless, still anger or stagger NPCs here (they fly in every game now: above); how far apart the group may be.

## Nothing of the session in a save

A friend keeps their own save, and nothing of the session goes into it. The sister project learned that a stand-in written into a save comes back broken, and crashes the game when its base was made at run time. Here:

- A stand-in's base is an NPC of the load order, so even one that a save did keep would load as a plain actor, not a crash. One that stands on a copy of its preset (its friend's face) is given the preset back as its base on its way out: at the step that deletes it (its 3D gone) and, for every one not yet gone, before a save is written. The save never holds an actor on a form made at run time, and the co-save names the preset as its base.
- SKSE tells the plugin a save is about to be written (`kSaveGame`), before the game writes it. Every stand-in is then disabled, so none stands in the world the save is made of; each is placed again a moment later. It is deleted a second later, not at once: a stand-in disabled and deleted in the same frame crashed the game (the disable's own task, run later, found the actor already out of its cell). Every way a stand-in leaves (its player leaves, the session ends, it goes out of range, its looks change, a save) takes the same two steps (`src/game/Retire.h`), so a save may still hold a disabled stand-in; the next point removes it.
- The co-save lists the stand-ins taken out. After a load, any of them the save brought back is removed, and so is any other placed actor of a preset base (a sweep, for a save written before this guard ran).
- The rig checks it: a friend saves mid-session, loads that save alone, and the plugin's `strays` count is 0. The load's log line says whether anything had to be removed, and by which of the two.

## NPCs

Written (protocol 6), not run in a game yet; the rig step `npcs` is ready for it. The sister project's design ("Shared NPC AI" in its DESIGN.md), carried over: each NPC near a player is run by one game, its AI included, and every other game shows a copy of it moved by that game's word. Nobody's game runs a world of its own, and no game waits on another to move an NPC its player is fighting.

- **Who runs it** (`common/NpcBook.h`, on the server; `src/game/NpcRules.h`, what each game asks for). An NPC nobody runs goes to the first game that asks; the game whose player is nearest asks first. A game whose player fights it (a hit, being its combat target) or talks to it takes it over, so that player's blows land on the real NPC at once, unless it changed hands, or its runner's own player fought it, in the last 5 seconds: two players fighting one NPC leave it with the first instead of trading it back and forth. An NPC that follows a player goes to that player's game, unless it follows the runner's player too. The runner says its NPC follows its player when it starts following and every 15 seconds after, however the runner got it (a follower hired after its game had it is held as one too), and says so when it stops (dismissed): the server holds it as a follower only while it keeps hearing so. A spawn (a reference a game made as it ran that its player or an NPC it runs commands: every summon, raised corpse and thrall, whoever cast it) is only ever its spawner's, and stays so while that game has it loaded. A runner lets go of an NPC it no longer has loaded, or whose player went 6000 units off with a friend 1000 nearer, so it runs where it is seen from close by; that friend's game asks for it, and no other game asks for it while it would let go of it again at once (no trading back and forth when the friend's game does not have it); a player who leaves lets go of all of theirs. The server tells everyone who runs what (`kNpcOwners`) and passes on only a runner's word about its NPCs.
- **What the runner sends**: where each NPC is and how it moves (position, angles, the graph's Speed and Direction, a few flags), 20 times a second in a fight or within 3000 u of a player and 10 otherwise (`kNpcStates`, numbered for the whole session, so a runner that has an NPC again after a moment without it goes on from its last number and its copies take its states at once; a copy also starts its states over whenever the NPC changes hands); the events its graph takes (an attack, a block, a shout, a dragon's take-off), heard by a hook on the actor's graph-event notify (`kNpcActions`; the hook chains to any other plugin's hook of the same slot, so the load order does not matter); and what it wears and holds when that changes (`kNpcGear`).
- **A copy** is that NPC in the other game, or for a spawn an actor placed from the spawn's base. While its runner's states are recent and in this player's space, its AI never runs: the same actor update hook as a stand-in's places it where its runner had it a short delay ago (`StateBuffer`), its graph's Speed and Direction come from the runner (`GaitDrive`), its walk's events come from `Gait`, and the runner's other graph events are played at the same point of its walk (`NpcRules::ActionQueue`). Otherwise (the runner on a loading screen, the NPC through a door this player did not take) it is left to its own AI until the states come back. Whenever a copy is let go of (that, the NPC run here now, the session ended), the move flags the hook wrote are cleared and its graph is sent back to its default state (`IdleForceDefaultState`), unless its own state says it really sits, sleeps, rides, bleeds out or is dead: its runner's last events (a furniture idle, a stagger) would otherwise leave it in a state its own AI cannot leave, and a load-order NPC would keep that in the save.
- **Gear**: a copy takes off what it wears or holds that its runner's NPC does not (a torch put away, a helmet taken off, a bow swapped for a sword) and puts on what it does, both hands (one weapon in both needs two of it). A copy of a load-order NPC is a real NPC of this game and goes into its saves, so it only equips what it already carries; nothing is added to it, and what it puts on is not held on against its own AI (no "prevent removal" lock that would stay in the save). A spawn's copy is this game's own and never saved (the save guard takes it out, as it does a stand-in), so it is given what it lacks. What the runner's game could not name to this one (a form made as it ran, a mod's this game lacks) is sent as unnamed, with the body slots of worn items, and the copy keeps its own there: never naked for a mod the other game lacks. The same where the runner's NPC wears or holds something this copy lacks (a leveled outfit rolls differently in each game: hide armor in one, fur in the other): the copy keeps its own in that body slot or hand, so a bandit is never stripped bare or left barehanded. A copy left to its own AI for a while is dressed again when it follows its runner again. What a copy wears and holds is read back from it after it is dressed (an equip the game refused, an item left on), and the developer channel says whether it is all on but what it lacks.
- **Every kind** is run and copied the same way: people, creatures, dragons (pitch too while flying), horses, followers and summons. The developer channel's `npcs` names the kinds a game sees, so the rig can tell which it covered.
- **Not shared yet**, each a later piece of work: actors a quest or an encounter makes as it runs (each game makes its own; they are counted as `unshared`); the leveled look and outfit roll of a leveled NPC (each game rolls its own); spells in a copy's hands; a dragon's flight graph, to be checked in a game; kill moves and ragdolls of copies (below); copies sitting in furniture.
- On the rig: `npcs`, `npcs list` and `npcs <form id>` (developer channel) say who runs each NPC, where it is and where its copy is; `tools/rig/steps/npcs.sh` checks both games agree on every runner, copies stand where their runners have them, and NPCs change hands when a player walks away, both ways.

## NPC health and deaths

Written (protocol 8), not run in a game yet; the rig step `npccombat` is ready for it. The sister project's health design (its `docs/HEALTH-SYNC.md`, reached after five rounds of "heal on hit"), carried over: the game that runs an NPC is the only truth of its health and its death, and no game ever undoes a hit it is still waiting on.

- **A hit on a copy** (our player's: its hit event names our player as the cause) is a numbered request to the NPC's runner (`kNpcHits`): the share of the copy's most health it took, so a hit takes as many to kill in every game however each game rolled the NPC's level, with what kind of hit it was (power, sneak, bash, spell, killing, kill move). The server sends it to the runner by its own book, not the hitter's (which may be a round trip behind), and answers it itself when it can go nowhere: nobody runs the NPC, the hitter does now, the session has it dead, or the hitter is past a budget of 64 at once and 20 a second (`kNpcHitAnswers`: never dropped). The runner takes the same share of its NPC's most off it, the hitter's stand-in its attacker (its killer when it dies of it), and answers applied with its NPC's health after it. Each hit ends in exactly one answer; one never answered is given back after two minutes, the one timer left.
- **What a copy shows** (`src/game/CopyHealth.h`) is the runner's word (`kNpcHealths`: said when it starts running the NPC, at once after a friend's hit it applied, and on a change of more than half a percent at most four times a second) less our hits not answered yet. So a copy is never healed for a hit still on its way, a refused hit is given back at once, and a runner whose NPC took less than the copy did (its own armor's roll) is believed, never sent again as more hits: a hit event explains one drop (within a second), and our player's lasting effects on the copy (a burn, a poison, an enchantment's, a concentration spell's: active effects our player cast that take its health) explain only their own share as they tick, at their magnitude, never any drop in a window after a spell. Anything else that changed the copy (another NPC's blow, a trap, a fall, its own regeneration) is set back once it has stood a tenth of a second: those are dealt in the runner's game, to its NPC. A fight between NPCs two games run is dealt in the game that runs the one hit, by the attacker's copy there, so it is counted once. A living copy is never set below one point of health: a runner's NPC down at none (an essential one) is no death here.
- **Deaths**: only the runner's counts, once (`kNpcDeaths`, with the player whose hit killed it, and whether it was a kill move); the server drops a second report of a death and any from a game that does not run the NPC. Each game sends its deaths and its answers to hits before its claims and releases, and the server still takes a death from the game that ran the NPC for three seconds after it lost it (another game's fight claim, or its own release, came first): every game hears that one, the game that said it too, and the new runner kills the NPC it has alive (its word of it alive in those seconds was said before it heard, and is dropped). An NPC nobody runs that dies in a game that saw it alive this session (our player's kill, a follower's, a trap's) is claimed by that game as a fight, and its death said once it runs it. A copy our player killed (its killer is our player, however late the hit event comes; a kill move counts as ours only when our player is its partner) stays dead here and its killing blow goes to the runner as all it stood at, so it dies there too. A copy its runner's death reaches is killed, after any kill move it is in (the move kills it itself). A runner that raises its NPC (a spell, a script) says its health again, and the session has it alive: a copy dead here while its runner's NPC lives is raised after five seconds, if it was seen alive here this session or this game is not the host's.
- **A body is the host's save's**: the server keeps every NPC the session has dead and the last word of each NPC run now for whoever joins after. Every game kills an NPC alive in it that the session has dead as it loads, but the host's game keeps its own save's word on a death it said itself (from an older save, that NPC lives). A body in the host's save that a friend's game runs alive is killed in that game (the host's game sends it a killing blow); a body in a friend's save that the host's game has alive is raised.
- **Not yet**: a stand-in's blows on NPCs (stand-ins do not attack yet; when they do, their blows must deal nothing, the friend's own hit is what counts), a kill move played on the runner's NPC by the stand-in, the ragdoll's push, essential NPCs' bleedout on copies, and a hit re-sent when the runner's book was behind.
- On the rig: `npcs` counts the hits sent, answered and given back, the healths and deaths said and heard; `npcs list` and `npcs <form id>` give each NPC's `hp=`, a copy's runner's `word=` and hits `inFlight=`, and whether the session has it dead (`sessionDead=`, `killer=`). `tools/rig/steps/npccombat.sh` checks a hit on a copy reaches its runner, both show the same health, a change no hit explains (the hitter's console's damage and restore on the copy) is set back to the runner's word, the hits kill it in both with the hitter its killer, and a raise and a runner's own kill reach the copy, both ways, a creature one way and a person the other; and that an NPC killed while the VM is out of the session is dead in the VM's game when it joins again.

## Loose objects

Written (protocol 17), not run in a game yet; the rig's repro is in the pull request that added it. The sister project's "Moved objects", carried to Skyrim's Havok bodies (`src/game/LooseObjects`, `src/game/ObjectRules.h`, `common/ObjectBook.h`): a loose object ends up in the same place in every game, whoever moved it.

- **What is shared**: a reference of the load order (so a mod's clutter is named as the stack names every form, by its plugin and its id there) that is not an actor, a projectile, an explosion or a hazard, is enabled and loaded, is held by no quest alias, and has exactly one rigid body whose motion type physics moves (dynamic, sphere, box or thin-box inertia). It is judged by its physics, never by a list of forms: a tankard, a cabbage, a bucket, a mod's clutter are shared; a door, a lever, a trap's moving part (keyframed) and statics never are. Not yet: objects with several bodies (a skeleton's bones, a chain), items a game drops as it runs (references made at run time: the drops pull request names them, and the message keeps a kind for them), and bodies (below, "Bodies").
- **Who reports it**: the game whose player, spell or NPC moved it. Our player's grab (Z, telekinesis) is ours; so are the hits (the hit event's cause), explosions (an `Explosion::Update` hook notes the update whose start found its forces not applied yet and whose end found them applied, so each explosion once, with its radius and the actor that set it off; no address is kept, since a later explosion often reuses a freed one's), projectiles' paths, bodies standing by it (160 u for a player, 200 for an NPC), dead bodies falling, and loose objects in flight, of our player and of every NPC this game runs. A friend's stand-in, a copy of an NPC another game runs, what either launches, and an object a friend's move sent flying are theirs. A projectile's path comes from its own updates (Shots' hook of the seven classes calls a watcher after each update of every projectile that flies, a friend's launch shown here included, never a native ended before it moves): a stretch every 100 ms and its last as it ends (no update for 250 ms), so a fast arrow that launches and sticks between two looks is still a cause, 256 u either side; a cone (Unrelenting Force) is its whole line at its first update, as far as its record's range (at most 4096 u), 512 u either side. Whose a path is comes from its shooter, on the main thread. A dead body's fall is the path of the middle of its 3D's bound from look to look (8 u or more), as far as its bound's radius reaches (64 to 400 u), its runner's: a ragdoll falling on a table makes the clutter it throws its runner's to report. A loose object in flight is a cause along its path from look to look, as far as its bound's radius and 32 u (32 to 256): ours while we watch it (our throw, or a move of ours), the friend's while their move of it keeps it quiet here. Every look is taken first and every path added, then each move is judged, so the order of the looks never matters. Four times a second the loose objects within 1500 u of our player are looked at (statics, trees, grass, flora, doors, furniture and containers are passed over before their 3D is walked); one that moved (1 u, or 0.02 rad) is ours to report when our strongest cause that reached it (a grab over a hit, blast or path, a fall or a flight over a body) is at least the friend's. A tie is ours: both games may report it, and the server keeps the first.
- **What is sent**: while our player holds something it is said 15 times a second while it moves and twice a second while still (`kObjectHolds`, on the state channel), in our player's frame (right, ahead, up and a rotation relative to the heading), so it is drawn in front of the friend's stand-in however each game placed it. A friend's held object is keyframed in our game, taken out of collisions while it is drawn (as the grab takes its object out of the holder's way: keyframed, it would shove our player and the clutter it passes), and eased to that place. Telekinesis is a grab too: what our player holds is the grab's object, or else the object of a telekinesis effect active on our player (`TelekinesisEffect::grabbedObject`), held from up to 4096 u away. If our player grabs what a friend holds, our player lets go (the grab's springs go; a telekinesis holding it is dispelled), and when the server answers our hold with a friend's (both grabbed it at once, the first wins) the same. A hold heard less than 0.5 s after its holder's let-go or rest of the object is late (holds go on the state channel, rests on the reliable one) and is not drawn, so a throw is never pulled back into the holder's hands. 80 ms after a let-go we say where it left the hands and how fast (`kObjectRests`, `kLetGo`, the velocity from those 80 ms, capped at 5000 u/s): the copy is put there with that velocity and flies on in each game's physics. Once a move of ours comes to rest (it moved under 1 u and turned under 0.02 rad for 0.6 s, never sooner than 0.3 s after it began, or 15 s after it began whatever it does) we say where (`kRest`), and every game puts its copy there. A pickup by our player is said (`kGone`), so nobody keeps a place for it. Only rests are sent for knocked objects, never transforms while they fly: two games' physics never agree in the middle of a flight, and the rest is what a player sees after.
- **Rate limits**: rests go out 8 at once, then 3 a second (one that waits 24 s is dropped and counted; a newer rest of an object waiting replaces it, never its let-go); the server takes 20 holds a second from a game and 24 rests at once then 6 a second, and keeps the rest owed (at most 256 a game), never dropped.
- **The server** (`ObjectBook`): one holder at a time, the first grab wins; a second game's hold is refused and answered with the holder's, so that game lets go and draws the holder's. A let-go is only its holder's, and its thrower owns its flight for 12 s or until its rest. The first rest of a move stands for 3 s: another game's rest within that is refused and answered with it, to that game alone. A rest of a held object, or of one another game's throw still flies, is refused. It keeps where each object came to rest last (at most 2048, the one moved longest ago forgotten first; one player may add 512 new ones a run), and what is held or thrown now (at most 1024: past that the moves that are over are forgotten, and while all are live a new object is refused).
- **What comes in**: a rest or let-go is put only within 8000 u of our player, in the same cell or worldspace, never more than 8000 u from where the object lies here, and only when it does not lie there already (1 u, 0.02 rad). A friend's rest ends any "still ours" window our own rest of it had. After a friend's rest our physics settling it is not ours to report for 4 s (12 s after a let-go), and at most 3 of our rests of one object go back against a friend's in 2 minutes, so two games that never agree on where a thing balances stop trading it.
- **Carrying**: the copy is drawn in the holder's frame before the stand-in every frame, so it follows the holder as they walk and turn, and falls or flies from where the let-go says. When the stand-in is in another cell than the copy (an exterior cell's border, or a door both went through) the copy is moved into the stand-in's cell (`MoveTo`, at most once a second) and drawn there, keyframed and out of collisions again (its 3D may be made anew; what it was is read once, at the first hold). When the stand-in is not here (the holder went through a door alone) the copy falls where it is until the stand-in is back. On the holder's side, a held object that is gone from what is loaded as the hands leave it (it stayed behind the door) is said to rest where it was held last, in the cell it was held in. A rest in another cell than our copy lies in (carried through a door in the mover's game) brings our copy into our player's cell when that is the rest's (`MoveTo` our player, then put once its 3D is there); else it waits until we are there. When the hold ends the copy gets back its motion type and collision layer as they were, so it is pushed, picked up and activated as before.
- **Late joiners and loads**: a joiner is sent every kept place (the session's word); after a load or a new game a game asks for them again (`kAskObjectRests`). A place for an object not loaded here waits (at most 4096) and is tried each second as the player comes near it.
- **Writing physics**: only on the main thread. A put moves the reference and its body together, as the sister project's does: first the reference's place and angles (`TESObjectREFR::SetPosition`, `SetAngle`) and its 3D and collision with them (`Update3DPosition`), then the body under the cell's Havok world lock (`bhkRigidBody::SetPositionAndRotation`, in Havok units via `bhkWorld`'s scale) with its velocities, and the reference marked moved by Havok. A body moved alone would, asleep, collide where its mesh is not, and the save and a cell's reload would put the reference back. The reference's place for a body's pose keeps where the body lies in the reference's frame (its collision may sit off the root), measured before each put. Two engine conventions are learnt from the objects looked at rather than assumed: how a 3D's world rotation and a body's quaternion map onto each other, and how a reference's angles make its 3D's rotation (each settled after 3 looks one way and none in ten the other; until then only the body is written, and counted). A pose that is not finite is never said or written. A friend's held copy has its body written every frame and its reference 20 times a second (enough to keep the mesh with the body if the engine does not draw a keyframed body's moves itself), and once more where it is when the hold ends. Every copy held keyframed for a friend is made dynamic again before a save, a load, a friend's leave and the session's end, so no save keeps a frozen object.
- On the rig: `objects` (developer channel) counts holds, let-gos and rests said, heard and put, waiting places, refusals, quiet and echo stops, causes and the explosion hook; `objects grab` says what our player holds (grab or telekinesis, its body and our player's place); `objects held` lists each friend's hold drawn here (our copy's body, where the hold puts it before the stand-in and how far from it, how far the drawn copy trailed that at most, the longest wait between two holds); `objects probe <id>` gives a reference's body, motion type and what this game knows of it, and whether the reference, its 3D and its body agree (`refTo3D`, `anglesTo3D`, `bodyTo3D`, each near 0 after a put); `flights` counts the projectiles followed and their stretches (and cones), `bodyFalls`, `ourPaths` and `theirPaths` the falls and flights made causes; the counts end with the two conventions learnt; `objects near [radius]` lists the loose objects near our player.

## Bodies

Written (protocol 19), not run in a game yet; the rig's repro is in the pull request that added it. The runner of an NPC is the truth of how its body fell and where it lies (`src/game/Bodies`, `src/game/BodyRules.h`, `common/BodyBook.h`).

- **The runner's**: every death this game says (one it ran as it died, and one that died here while nobody ran it, said once its claim is granted) is watched. Its fall is said once its ragdoll starts, so it carries the blow's velocity and not the death animation's, or 1 s after the death if no ragdoll came (`kBodies`, `kFall`): its pelvis's velocity, capped at 5000 u/s. Its ragdoll is watched four times a second until it settles (no bone moved 2 u for 1 s, never sooner than 0.5 s after the fall, or 10 s after it whatever it does), then its bones are said (`kRest`): every ragdoll bone, by a hash of its node's name (the skeleton is the race's, the same in every game), with its place and rotation. A body is said whole or not at all: one with more than 96 bones (a dragon's has several times a person's 15), a bone named twice or one gone wrong is not said, and counted. The skeleton is walked whole (an extended skeleton has hundreds of nodes). If the NPC changes hands while its body settles, its rest is still said by the game that said its fall.
- **A copy's**: a fall heard is pushed once the copy died here and is in its ragdoll (every bone given that velocity), within 3 s of hearing it. A rest heard is laid once the copy has been dead here for 2 s (its own fall is over), is loaded in the same cell or worldspace within 4096 u of where the runner's lies, and lies more than 96 u off somewhere (two games' ragdolls rarely fall the same; a few units is not worth a twitch). It is laid whole or not at all: only when every ragdoll body of the copy is named once in the rest (a rest may name bones this game's skeleton lacks), since a ragdoll some of whose bones are moved far from the others is pulled back together by its constraints with huge impulses and tears itself apart. The actor's reference is moved first to where the runner's lies (loot, activation, a cell's reload and the save follow the reference, not the bones), then every bone is written where the runner's lies, with no velocity, under the cell's Havok world lock, and the actor is marked moved by Havok. The bones are read back: if one came out not finite or is gone, every bone is put back where it lay, and it is logged. A copy this game runs by then is its own truth.
- **The server** (`BodyBook`) passes a body on only from its NPC's runner (or from any game while nobody runs it), (and a rest from the game that said its fall, if the NPC changed hands since), only while the session has the NPC dead, 16 at once and then 4 a second from a game; past that a body is owed (at most 256 a game) and passed on as the budget allows, never dropped. It keeps each body's last rest (at most 512, the one laid longest ago forgotten first) for a joiner, and sends them again with the loose objects' places when a game asks after a load; a body the session has alive again (raised) is forgotten.
- **Not yet**: kill moves on copies, and bodies of NPCs nobody shares.
- On the rig: `bodies` (developer channel) counts deaths, falls and rests said and heard (and falls read before a ragdoll started, bodies not whole, handed over), falls pushed and late, bodies laid, moved, left, not laid whole and put back; `bodies probe <id>` gives an actor's bones, its pelvis's place, velocity and motion type, and whether it is dead and in its ragdoll.

## Quests

Not designed yet (phase 5). The aim is that every quest is shared: the stage advances for everyone whoever did the step, and the host's save keeps it. To settle: dialogue (who talks, what the others see), scenes written for one player, quest items, rewards, radiant quests, and the quests that cannot be shared as they are.

## The menu

Not designed yet. Phase 1 uses the ini and a key or console commands. A menu in the game (host, invite, join a friend, who is here) comes later. Skyrim's menus are Flash files in ActionScript 2, built from source like everything else; no compiled menu file is committed.

## Decisions to confirm

Choices made to keep moving. Each is the obvious option, cheap to change now, and the maintainer's to confirm or overturn.

| Choice made | The alternative |

| CommonLibSSE-NG (`alandtse/CommonLibSSE-NG`), pinned to a commit of its `ng` branch, built from source with Skyrim VR support off. | Another maintained fork of CommonLibSSE (for example `libxse/commonlibsse`), if it follows new game versions sooner. |
