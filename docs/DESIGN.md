# Design

How SkyrimCoop is meant to work, and why. This is a skeleton: the decisions that are made, the parts that exist, and for everything else a heading that says what has to be decided there. A section is filled in when its phase of [PLAN.md](PLAN.md) is built and tested, with what the game turned out to do, not before.

Nothing here has been run in a game yet.

## The idea

A small group of friends plays through Skyrim together in one world.

- **One host, whose save is the world.** The host loads their own save and plays. Friends join it. Quests, the state of the world, the time of day: the host's game decides, and the host's save keeps it.
- **Friends follow.** A friend plays their own character, with their own gear and skills, kept in their own save. Their save keeps the character, not the world: what the group did lives in the host's save.
- **Steam first.** The host's game opens a friends-only Steam lobby. A friend joins from the Steam overlay or the friends list. The games talk through Steam's relay network: no server to rent, no port to open, no address to pass around.
- **By address second.** A direct UDP connection to an address and port (a LAN, a forwarded port, a VPN of the group's own choosing), and a dedicated server for those who want one. The same session either way.
- **Tested for hours before it ships.** A release is a release candidate that two scripted games played for a long session without a failure ([RELEASING.md](RELEASING.md)).

It is the design of [F4Multiplayer](https://github.com/Jolley71717/F4Multiplayer), the sister project for Fallout 4, moved to another game by the same engine family. Where that project has an answer that does not depend on the game, this one starts from it.

## Decisions made

| Decision | Why |
| --- | --- |
| The game is Skyrim Special Edition on Steam, the current version (the Anniversary Edition update line). Not the 2011 game, not Skyrim VR, not the GOG or Microsoft Store versions, for now. | One game version to reverse-engineer and test. Steam is how players join, so a version without Steam has no way in. |
| The plugin is an SKSE64 plugin built on CommonLibSSE-NG, finding the game's functions through the Address Library. | The same stack as the sister project's (F4SE, CommonLibF4, Address Library), so the same habits apply. Address Library ids survive most game updates. |
| The host owns the world; friends follow. | One source of truth. Two games that both decide drift apart, and no save can hold two worlds. |
| Steam lobbies, invites and the relay first; join by address second. | The reason for the project: joining should be an invite, not network administration. |
| Steam is reached through the game's own Steam library, by hand-declared functions found at run time. The Steamworks SDK is never in the repository and no Steam library ships with the mod. | The SDK's terms do not fit a GPL repository, and the game already has Steam loaded under its own app id. |
| GPL-3.0-or-later with the modding and linking exceptions, as F4Multiplayer. | The same license lets code move between the two projects, and CommonLibSSE-NG's license asks for it. |
| No code from other multiplayer mods. | Their licenses differ and some allow nothing ([PRIOR-ART.md](PRIOR-ART.md)); whether to build on any of them is the maintainer's decision, not a contributor's. |
| Game-free code is kept apart (`common/`) and unit-tested on every pull request; anything that touches the game is tested on two real games. | The split the sister project relies on: most protocol bugs are found without a game, and no game behaviour is taken on trust. |
| A release candidate first, then a long two-game test of exactly that build, then the release. | What is tested is what ships. |
| Logs name no person and no machine. | A bug report's log is attached in public. |

## What exists today

```
        game A (host)                                   game B (friend)
  +--------------------------+                   +--------------------------+
  | SkyrimCoop.dll           |                   | SkyrimCoop.dll           |
  |  src/main.cpp  start-up  |                   |                          |
  |  src/game/*  stand-ins   |                   |  src/game/*  stand-ins   |
  |  src/net/NetClient ------+--- transport -----+-- src/net/NetClient      |
  |  common/Server (thread)  |   Steam relay or  |                          |
  |  src/steam/*             |   UDP (ENet)      |  src/steam/*             |
  +--------------------------+                   +--------------------------+
```

- **Start-up** (`src/main.cpp`): keeps the last three logs, starts the log, checks the game's version (`src/RuntimeSupport.h`), reports how the game was started (`src/LaunchReport.h`, `src/Platform.cpp`), reads the ini (`src/Settings.h`, `src/Config.cpp`), and listens for SKSE's messages: data loaded, before and after a load, new game, save, delete. Its co-save ("SKCO") holds two records: the stand-ins taken out of the world for that save (below, "Nothing of the session in a save"), and the loot ledger (below, "Containers and loot").
- **The protocol** (`common/Protocol.h`): a first, small one. A hello with the mod's protocol version, the player's name, a password and the load order; a welcome or a refusal with its reason; the session's plugin table (each plugin a place, sent to every game as it grows); players joining and leaving; each player's state (cell or worldspace, position, heading, speed, a few flags, the sender's clock); each player's looks (race, sex, weight and the armor worn, as form ids), which the server keeps and gives to whoever joins later; a heartbeat. Two channels: reliable, and unreliable-sequenced for state.
- **The server** (`common/Server.cpp`): lets players in (same protocol version, the right password, room left; any load order whose plugin list it has), gives each an id, keeps the session's plugin table, and passes each player's state and looks to the others. It runs as a thread inside the host's game, or alone as `SkyrimCoopServer.exe`.
- **Transports** (`common/Transport.h`): the session does not know how bytes travel. `common/EnetTransport` is UDP through ENet; `src/steam/SteamTransport` is Steam's relay messaging; `tests/FakeTransport.h` is memory, for tests.
- **Steam** (`src/steam/`): the lobby, invites, "Join Game", friends who are hosting, carried from the sister project. Not yet shown to work under Skyrim ([GETTING-STARTED.md](GETTING-STARTED.md), "The first thing to test").
- **The session in the game** (`src/net/Session`): hosting runs the server in the game, reached by friends through Steam and by the host's own connection over UDP on this machine only; a friend joins from Steam itself (an invite, "Join Game", a `steam://joinlobby` address, or the lobby on the command line Steam starts the game with, `src/net/LaunchArgs.h`). Once in, each game sends its player's state 20 times a second and its looks when they change.
- **The game side** (`src/game/`): the load order (`LoadOrder`), the local player (`LocalPlayer`), the other players' stand-ins (`RemotePlayers`, with `StateBuffer` and `Gait`), the frame (`GameThread`, still the stand-in tick) and, for the rig, a virtual gamepad (`VirtualPad`) and console commands (`Console`). [PORTING.md](PORTING.md) has a section for each.
- **Privacy** (`common/Redact.h`): players are `player N` in every log line; addresses are masked; a last scrub runs over every line.

## Sessions

Carried from the sister project and unit-tested:

- A friend is let in only with the same protocol version and the host's password. Each refusal has its own reason, shown to the player.
- Load orders may differ (since protocol 4): other mods, or the same ones in another order. Only a hello without a plugin list (a tool's, or a load order too long for a hello) must have the session's load order, since nothing can translate its forms. The first player in the session sets the session's load order; on a hosted game that is the host.
- Each game has a random identity kept on its PC; a player who drops and returns gets the same player id. It is not a Steam id and says nothing about the person.
- Up to 8 players by protocol, 4 by default.

To design when phase 1 is built: what a friend sees while joining, joining in the middle of a fight or a scene, the host leaving, a friend's game crashing, bans.

## Form ids across load orders

Every object in the game is named by a form id whose first byte (or, for light plugins, bits) depends on the load order. Two games with other mods, or the same mods in another order, give the same object other ids. So no game's ids go over the wire (protocol 4, the sister project's design):

- **The session's plugin table** (`Protocol::PluginTable`): the first player's load order, with the plugins each later joiner brings added after the rest of their kind (`FormIds::Extend`), so an id it gave never changes. The server sends it to each joiner before the welcome, and to everyone in whenever it grows, on the reliable channel.
- **A form on the wire** is its plugin's place in that table and its number within the plugin: a plugin is named by its file name, never by where any game loads it.
- **Each game translates at its edge** (`common/FormTranslate.h`): every packet out from its own ids to the session's, every packet in from the session's to its own, by plugin name (`FormIds::Mapper`), before anything reads it. The rest of the game only ever sees its own ids, the server only the session's. With the same plugins in the same places (the usual case) no id changes.
- **A runtime form (FF) is never sent as a form.** A game makes them as it runs (a brewed potion, a form a mod's script or SKSE plugin creates), so the id names nothing in another game, or that game's own runtime form of the same number. A sender sends the plugin form it was made from instead where there is one (an armor's template, `FormIds::Shareable`); the edge skips any runtime id left in a message, both ways, whatever the load orders (the identity too); and a receiver never looks one up (`RemotePlayers::Dress`, the race). An item's own enchantment (a player-made one is a runtime form in the item's extra data) is not carried yet.
- **A form of a plugin the other game lacks is skipped, never guessed**, and the message still goes: a place (a state's cell and worldspace, as a pair) becomes "nowhere this game has" (both 0), so no stand-in is shown in the wrong world; a worn item is left out; a race becomes none, and the stand-in is a Nord. Each such plugin is named once in that game's log. A plugin full in one game and light in the other maps too, but for its forms past the 4096 a light plugin can number.
- The server's log says only how a joiner's load order differs (counts); each game's own log names the plugins.
- On the rig: the `forms` developer command (`src/net/FormsCommand.h`) reads a game's edge, and finds a form by plugin file name and number; `tools/rig/steps/forms.sh` (the harness's step `forms`, run only when named) puts two plugins of the VM's game in another order and checks gear crosses both ways, on the stand-in actor itself (`standins` lists its `equippedIds`).

To decide later: a host option to refuse friends whose mods differ (the sister project lets the host ignore some plugins in the comparison; it would also stop a friend who is let in from filling the session's plugin table with made-up names, which only grows until everyone leaves), and telling a friend in the game which plugins differ (the sister project's ModDiff, with the menu).

## The frame

Everything that reads or changes the game happens on the game's main thread, once per frame; network threads only queue. The stand-ins' movement does not wait for the tick: they are placed inside their own actor update, which the game runs every frame. SKSE offers no "every frame" call, so the plugin needs a hook in the game's main update. Not written yet ([PORTING.md](PORTING.md), "The frame"). Until it is, a stand-in tick serves the first test: a small thread asks SKSE's task queue every 16 ms to run the plugin's tick once on the main thread, one request at a time. It is not tied to the game's frames and may not run in every game state; it is replaced, not built on.

## Players

The first stand-in (`src/game/RemotePlayers`), kept simple on purpose:

- **What it is**: a plain NPC of the friend's race and sex, wearing the armor they wear and named as they are. Its base is one of the game's own character-creation presets of that race and sex (the lowest form id, so every game picks the same), an NPC of the load order: never a form made at run time. Faces, hair and body come later.
- **How it is moved**: the game never runs its AI. Every Character's actor update goes through one hook (the class's vtable, `Actor::Update`); for a stand-in it places the actor where its friend was 120 ms ago (blended between the two states either side, `StateBuffer`), turns it, runs the engine's no-AI update and tells its animation graph what its friend's legs do (`Gait`: the graph's Speed and Direction, and its move, sprint, sneak and jump events). Any other actor gets the game's own update.
- **Its legs**: the engine does not keep a Speed or Direction set on an actor's graph. Each time the graph updates it pulls both through a channel per variable (`BSTAnimationGraphDataChannel<Actor, float, ActorSpeedChannel>` and `<..., ActorDirectionChannel>`) from the movement speed and direction in the actor's process, and the actor's movement job sets those every frame from its movement controller's desired movement: none, for an actor whose AI never runs. So a stand-in's graph read 0 and it slid along with its legs still. The two channels' polls are hooked (their vtables, by Address Library id): after the engine's poll, a stand-in's channel holds its friend's Speed and Direction, as its own update last wrote them (`GaitDrive`; values not written for half a second go back to the engine's). The movement controller is left alone, so nothing moves the stand-in but its friend's states.
- **When it is there**: while both players are in the same interior cell or the same worldspace and within about two cells of each other.
- Open, for later: guards, factions and crime; mounts, shouts and transformed forms; two hands; how far apart the group may be.

## Nothing of the session in a save

A friend keeps their own save, and nothing of the session goes into it. The sister project learned that a stand-in written into a save comes back broken, and crashes the game when its base was made at run time. Here:

- A stand-in's base is an NPC of the load order, so even one that a save did keep would load as a plain actor, not a crash.
- SKSE tells the plugin a save is about to be written (`kSaveGame`), before the game writes it. Every stand-in is then disabled, so none stands in the world the save is made of; each is placed again a moment later. It is deleted a second later, not at once: a stand-in disabled and deleted in the same frame crashed the game (the disable's own task, run later, found the actor already out of its cell). Every way a stand-in leaves (its player leaves, the session ends, it goes out of range, its looks change, a save) takes the same two steps (`src/game/Retire.h`), so a save may still hold a disabled stand-in; the next point removes it.
- The co-save lists the stand-ins taken out. After a load, any of them the save brought back is removed, and so is any other placed actor of a preset base (a sweep, for a save written before this guard ran).
- The copies of dropped items (Dropped items, below) are taken out before a save the same way, named in the co-save and removed after a load that kept any. What a save keeps of the session is which of its drops left that world or came into it, so a load is made to agree with the session.
- The rig checks it: a friend saves mid-session, loads that save alone, and the plugin's `strays` count is 0. The load's log line says whether anything had to be removed, and by which of the two.

## Combat

Not designed yet (phase 3). The starting rule is the sister project's: the host's game runs every NPC and decides every hit's result; a friend's game reports its hits and shows what the host decided. To settle: melee timing over a connection, blocking and staggers, bows and spells in flight, kill moves, a player's death, friendly fire, levelled enemies when players differ in level.

## Doors, locks and mechanisms

Since protocol 5. Not tested in a game yet; the rig step `doors` is ready for it. The rules, free of the game, are `src/game/RefRules.h`; the game side is `src/game/WorldObjects`; the server's book is `common/RefBook.h`; tests in `tests/RefStateTests.cpp`.

**What is shared, by class.** Each reference is sorted by its base's form type and flags, never by its name or script, so every door, gate, chest and lever of every mod is covered the same way:

| Class | How it is told | What is shared |
| --- | --- | --- |
| Door (gates, portcullises, hatches) | a `DOOR` base without a teleport | open or closed, and the lock |
| Gate built as an activator (portcullises, drawbridges, gates a lever's script raises) | an `ACTI` base, named or not, whose reference has open and closed states (`BGSOpenCloseForm`) | open or closed |
| Load door | a door with a teleport (it leads to another cell) | the lock only: each player goes through on their own |
| Automatic door | the door's "automatic" flag | the lock only: it opens for whoever is near it |
| Container | a `CONT` base | the lock only (what is in it is for later) |
| Mechanism | an `ACTI` base with a name (levers, pull chains, pillars, buttons, wheels) | a player's use: their stand-in uses it in the other games |
| Anything else | markers, activators with no open state and no name, pressure plates | nothing: each game's own |

**How a change travels.** The game says what changed in its own events: a door opened or closed (`TESOpenCloseEvent`), a lock changed (`TESLockChangedEvent`: picked, opened with a key, locked or unlocked by a script or the console), our player used something (`TESActivateEvent`). The sinks only queue; the next frame reads the reference and reports what the session doesn't know yet. A report says only the part its change is about: an open or close says the open state, a lock change the lock and its level; the rest of what the reporting game reads is its own save's, and never overrules the host's world (a friend who opens a door that is unlocked in their save does not unlock the host's). As not every kind is known to send the open/close event (an activator a script opens), the open states within 2000 units of our player are also read twice a second, and a change between two reads counts as an event; a reference first read (come near, or loaded) is this game's as it is and says nothing. A change by our player is reported at any distance; one made by anything else (an NPC through a door, a script) only within 2000 units of our player, so two players far apart don't both report the same NPC's door. The server keeps the last word on each reference (up to 16384) and passes each report to every game, the reporter's own included; each game applies the session's word where its own reads otherwise. A game counts its own reports still on their way, so an old echo of its own doesn't undo a newer change of its own. Every report is answered: one the server does not take (past the player's budget, a full book, a report of nothing) goes back to its reporter alone with why and the session's word on it; the game then counts it answered, takes the session's word as what is known, and reports a busy one again a second later. Two players at one door at once end on the same word: whichever the server heard last.

**Lock levels** go as the game's six levels (novice to master, and "needs a key"). A lock the session sets is written at that level with its "leveled" flag cleared, so every game reads the same level whatever its player's level, also where the reference had no lock (one is added) or a leveled one that read no level.

**A friend's use of a mechanism** is made in each other game by the friend's stand-in (`ActivateRef`), so the lever's own script runs there: the gate it moves, the trap it springs. It is refused when the stand-in is not placed, or is more than 1000 units from the mechanism (it is somewhere else in that game), or when the game refuses the activation. Uses are not kept: one made before a player joined is not made again for them; what it changed (a door, a gate, a lock) is. What a use moves is moved by the script in each game, and the user's game reports it too: for 3 seconds after a use is made, words on open states wait and are applied after the script has run, and open states that change in that game without its player's hand are not reported. Otherwise a lever script that flips its gate would find the gate already opened by the word and close it again, and every game would end with it closed.

**Pacing.** Each game sends at most 8 reports for one reference at once and then one every 2 seconds (a door spammed open and shut, a script that loops), the latest held back and sent when due. The server allows each player a burst of 32 reports and 8 a second after that (past it, answered busy), 8 uses and 4 a second, and two asks for every word and one in 5 seconds after that (past it, the ask is answered when the budget allows, never dropped).

**Late joiners and loads.** A game that joins is sent every kept word right after its welcome. A game that loads a save (or starts a new game) asks for every kept word again and applies it: its save holds its own doors as it last saw them, and the session's word wins. A word on a reference not loaded in that game waits (up to 4096) and is applied when it loads, tried again every half second.

**Threads.** The game writes (a lock, an open state, a stand-in's use) are made from the plugin's tick, which until the frame hook is written runs on SKSE's task queue, seen on the task pool's job threads in the world. Each write made off the main thread is counted (`refs`: `offmain=`) and said once in the log; the frame hook moves them to the main thread.

**Rewards.** Since protocol 23. Not tested in a game yet. The rules, free of the game, are `src/game/RewardRules.h`; the game side is `src/game/QuestRewards`; tests in `tests/RewardTests.cpp`. A reward a stage's fragment gives (gold, the quest's item) is every game's already, as the stage is made in each. One a conversation gives (a topic info's own fragment: "here, take this") runs only in the game of the player who talks, so that game says it:
- An item that comes to our player from nothing (no container gave it and no reference was picked up: a script's `AddItem`) while the Dialogue Menu is open, or shut less than 2 seconds ago, with no barter, gift, container or training menu open or shut less than a second ago, is a reward of the quest of the topic info our player or whom it talks with said last (10 seconds at most), when the session shares that quest here. A key is not (it is the door's), nor an item that came less than 2 seconds after a stage of that quest this game made from the session's word (another player's step: its fragment gave it in every game). Several of the same item within a second are one reward, said a second after the last (`kQuestReward`, so its stage's report goes first). Each item from nothing is counted by what it was judged (`rewards`: `why=`).
- The server passes it on to the others with its player (`kRemoteQuestReward`) and keeps nothing: one who joins later gets none. A game says at most 32 at once and one a second after that; one said before its game heard the host's reset is of the old world, and dropped as its quest reports are. The host's game gives none heard between its load and its reset's answer.
- Every other game gives it to its player (`player.additem`) once the quest's stages from the session are made there and 5 seconds have passed since the last (its fragments ran), less what its player got from nothing since a moment before that stage (a stage the conversation set may give part of it everywhere; the talker's game cannot tell the two apart). So a reward of the conversation alone is given whole, and one its stage gave everywhere is not given twice. A quest not shared there, or never started there within 10 seconds (its stages held far and given up, or its own), gets nothing; a reward whose stages do not come within 2 minutes is dropped. Each is logged. A game's own gives are matched as they come back and are never said again.

**Not yet:**
- A mechanism whose script checks the user's inventory (a claw door, a key-only activator) may refuse a friend's stand-in, which carries no claw. The friend's own game opened it; the others' don't follow.
- The server does not judge whether a reporter could have reached what it reports.
- The session's book lives as long as the server runs; a session hosted again starts with an empty one.

## The world

Not designed yet (phase 4), beyond doors, locks and mechanisms (above), and time and weather and containers and loot (below). The host's world is the world: items lying about, harvested and mined things. To settle: what a friend who joins late is told, respawning cells, what a friend's save keeps, houses and Hearthfire.

### Time and weather

Since protocol 9. Not tested in a game yet; the rig step `clock` is ready for it. The rules, free of the game, are `src/game/ClockRules.h`; the game side is `src/game/WorldClock`.

**Whose clock.** The session's clock is the clock owner's: the host's game, or on a dedicated server the player there longest (the sister project's rule). Every game says its clock (`kClock`: the hour, the day count, the timescale, and outside its worldspace and weather) every 5 seconds, and within a second of a change (a weather, a worldspace, a timescale, or an hour or day that jumped: a wait, a sleep, a load, the console). The server passes on only the owner's (`kRemoteClock`), keeps the last one for a friend who joins, and drops anyone else's (logged once per connection). A kept clock whose owner left is not given to a joiner; a new session forgets it. At most 4 clocks a second go out per game, the newest owed when the budget is spent.

**Following the hour.** A friend's game keeps the owner's hour (and the 20 seconds after the owner's last word; after that it keeps its own until the owner speaks again):
- The first clock heard lines the two up: forward to the owner's hour, or back within the same day, never back across midnight (a friend's date never goes back).
- From then on the two day counts are kept a fixed number of days apart, and each move of the owner's (a wait, a sleep, the hours passing) is the friend's too. A move forward stops at 23.99 for the game to roll its own date over (its calendar and its timers see midnight), then goes on.
- The day count moves with the hour we set (`GameDaysPassed`), as it does when the game waits; a console `set gamehour` moves the hour alone, and is followed the same way.
- The two are lined up afresh when the offset no longer fits (the owner loaded a save, or set its hour by hand), when another player becomes the owner, when a move would be more than 72 hours, or when a move back would cross midnight.
- A friend's own wait or sleep is undone: back to the owner's hour within the day. Nothing is moved while that wait runs: the engine passes the hours itself with its Sleep/Wait menu open and ends the wait by the clock, so following holds until the menu shuts, and the owner's clock is lined up from where the wait left the friend. (Fast travel, a carriage, jail and training jump the clock at once with no menu running, and are followed like any other jump.) One that crossed midnight cannot go back without the date going back: that friend goes on to the owner's hour the next day. The owner's game never follows anyone.

**Timescale.** A friend's game runs at the owner's timescale. Its own is kept: it goes into its saves (set back just before a save is written, the owner's again on the next tick) and is set back when the session ends. A save loaded in the session has its own timescale, which is kept as the game's own from then on.

**Weather.** Only outside, under the owner's sky: in the owner's worldspace, or in one that uses its climate. The walled cities (Whiterun, Solitude, Windhelm, Riften, Markarth) are child worldspaces of Tamriel on its climate, as is any mod's world made the same way, so a player inside the walls and one outside share a weather; a world is compared by the worldspace whose climate it uses, walked up its parents (a weather is a worldspace's: a worldspace this game lacks has no weather either, and a weather made at run time is not sent). On arrival under the owner's sky the weather is forced at once; when the owner's turns, it is eased in as the game changes weather; an ease that has not taken after 30 seconds is forced. A weather this game's own script forced (an override: a quest's storm, a dragon's) is held, not fought, and logged once. The weather is set without an override of ours, so a friend's climate may roll its own weather between the owner's reports; it is eased back.

**The Helgen opening.** A game in the opening keeps its own clock and says nothing: the opening's scenes are timed by its own hour and weather. In the opening means `MQ101` running, not completed, and begun in that game (a stage of it set, or the player's movement taken away, as in the cart). A game put in the world another way (the console's `coc` from the main menu, an alternate start) that leaves `MQ101` running untouched is not in it. The plugin log says each time the opening starts or stops holding the clock, with the quest's stage, so a game that never follows or says a clock says why.

**Not yet:**
- A shout or spell that changes the weather (Clear Skies, Storm Call) in a friend's game is undone by the owner's; it does not reach the owner.
- A friend's save keeps the session's hour and date; loading it alone, outside the session, is that day.
- Weather inside (none) and under a sky other than the owner's (another worldspace on its own climate) is each game's own.

### Containers and loot

Since protocol 10. Not tested in a game yet; the rig step `loot` is ready for it. The rules, free of the game, are `src/game/LootRules.h` and the server's log `common/LootLog.h`; the game side is `src/game/LootSync`. Ported from the sister project's design, with Skyrim's own forms.

**What is shared.** The class is every holder a player loots, judged by what the engine keeps, never by a name, so a mod's chest is shared as the base game's are: every container (chests, barrels, sacks, urns, satchels, wardrobes, coffins, Dwemer and mod containers), and the body of every actor kind once it is dead (people, creatures, dragons, horses, a follower or a summon that died; an ash pile's remains are its actor's inventory). Shared items are the plain base forms: gold, weapons and armor (Skyrim's enchanted loot is a form of its own), ammo, potions and food, ingredients, misc items, soul gems, scrolls, torches. Each player's own:
- a living actor's inventory (a follower's or a horse's pack, a pickpocket's take);
- a merchant's chest (every faction's vendor container), and anything moved while the barter menu is open or for a second after it shuts;
- keys, books (notes, journals, skill books and spell tomes: each player reads their own) and quest items (a quest alias's object);
- an instance with extras of its own: tempered, enchanted or poisoned by a player, renamed, a soul gem a player filled. A move names the item's base form only, so another game would get a plain copy; the game's event names the stack moved (its unique id), which is how one is told from a plain stack of the same item;
- a runtime holder or item (FF: made by one game as it ran: a placed chest, a summoned body, a player's own potion).
Storage (a container or a cell the player owns: their house) shares its moves, but is never said emptied (below): what each player keeps there stays.

**A move.** The game's own event (`TESContainerChangedEvent`) says what our player moved: an item from a holder to the player (a take) or from the player into a holder (a put). It is queued by the event sink and read on the next frame, judged by the rules above, and reported (`kLoot`, up to 64 moves a batch; a Take All is one or two). The server numbers every move it takes in the session's log (`kRemoteLoot`) and passes it to every game, the reporter's own included, with who made it. A move it does not take goes back to the reporter alone (`kLootAnswer`) with why: busy (past that player's budget: 64 batches, then 16 a second; sent again a second later), full (the log keeps 30,000 moves), or refused (no holder, a runtime form, a form the session can't name). So every move a game sends is answered once. Each move carries a tag of the reporting game's own, which the server carries back as it was in the echo and the answer, so the game knows its own moves by the tag, in any order, even when a form came back as 0 (one the session can't name); a busy move goes again as it was sent.

**Making a move here.** Each game makes the others' moves in its own copy of the holder: a take removes as many plain stacks of the item as it holds, up to the move's count (never an instance of the item here); a put adds them. A move is made when the holder's cell is loaded here (an ash pile's or a disabled body's too); until then it waits, each holder's moves in the order heard (a put that waits holds back the takes after it). A move at a body alive here waits for its death, up to 10 minutes (another game's own fight this game never saw). The game judges every move again by its own facts, so what another build or another game's mods report anyway stays out. No move is made at a holder our player has open in the container menu: the menu's list holds that holder's inventory entries and reads them as the player takes or stores, and the tick runs on the task pool's job threads, so removing a stack there could free an entry the list still names (a crash, or a take of an item that is gone). Such a move waits until the menu shuts (the menu's own close event makes the game retry at once), and the moves after it at that holder wait behind it. Until then the player sees the copy as it was when the menu opened; an item both players take in that time is had by both (the later take finds fewer here, and takes what is left). LootSync's state is under one lock, taken by the tick and by SKSE's callbacks on the main thread (the co-save, a load); the event sinks never take it.

**Two rolls.** Each game rolls a chest's or a body's leveled loot on its own, so the same holder holds different things in two games. Moves are relative (take 5 gold, put 1 dagger), so each copy keeps what only its own roll has. When a player's take leaves their copy holding nothing the session shares, their game says so (an emptied marker, sent after the frame's takes, carrying its ledger as of then). Every other game then takes out of its own copy what is left of each item another player took from that holder since it was last emptied here (its roll had more of it), and leaves the rest: what only its own roll holds, what its own player alone took, and the session's puts the sender had not seen yet (numbered at or after the marker's ledger, or our own still on the way). Storage is never emptied by a marker.

**The ledger.** Each game keeps the number of the first move its world does not hold yet, and the log's id (a new session starts the log again under a new random id). It is kept in the co-save ("SKLT" in the plugin's co-save, with the moves still waiting for their holder), so a save loaded in a session asks the server for the moves from there (`kAskLoot`) and makes the ones its world lacks, its own among them (the load took them from its world), then hears the log's next number (`kLootCaughtUp`). A welcome asks the same way, so a friend who joins late, or again, catches up; a world that never was in a session, or was in another session, is answered from the first move. The world is replaced at a welcome and at a load, and from that moment, not from when the ask goes out (it can't from a loading screen), moves passed on are held until the catch-up is done: the catch-up brings them with the ones before, so the ledger never moves past a move its world lacks. Each ask has its own number, carried by its catch-up and its end; the answers to an older ask (asked for a world replaced since) are void, and the server owes a game one ask at most, the newest (a burst of loads past the ask budget leaves the newest owed, answered once there is room), so a game is never left asking. In a catch-up, our own moves made in this world since the load (their echoes were held) are matched by their tags and not made twice; ours made in a world a load replaced are made, as this world lacks them. A friend's save keeps the moves made in its copies: loading it alone, outside the session, it is as that player left it.

**Not yet:**
- Picking up an item a plugin placed in the world (an item on a table, a sword on a rack) is each game's own; dropped items are given (below).
- Harvesting (plants, ore veins) and a container's respawn: each game's own clock and rolls.
- A body made at run time (a dragon, a Story Manager spawn, a summon) is a runtime holder: not shared until the actors themselves are.
- A friend's move at a holder our player has open shows once the menu shuts, not at once: a live redraw needs the menu's own list rebuilt on its thread (the sister project hooks the menu for it), to be done and checked in a game.


### Dropped items

Since protocol 11. Not tested in a game yet; the rig step `drops` is ready for it. The rules, free of the game, are `src/game/DropRules.h` and the server's book `common/DropStore.h`; the game side is `src/game/DropSync`. Ported from the sister project's design (its drop book and store), with Skyrim's items, without its server file and its characters' keys (below).

**What is given.** A player gives an item by dropping it: it lies in every game's world, and the first player who takes it has it. The class is every item a player can drop, judged by its form type and its extras, never by a name, so a mod's item is given as the base game's are: weapons and armor, ammo, potions and food, ingredients, misc items and gold, soul gems, scrolls, torches. The item's extras travel with it: a tempered item's health, an enchantment on the item itself and its charge, a weapon's poison and its hits left, a soul gem's soul, a name the player gave it. Each player's own (dropped, it stays in their world alone, as before):
- keys and books, as in containers;
- quest items (a quest alias holds the reference);
- an item whose base, enchantment or poison was made at run time (a potion a player brewed, an enchantment a player made): no other game has that form;
- an item a plugin placed in the world, picked up and dropped again: its pickup is not shared yet, so a friend's world still has it where the plugin put it.
- an item a script drops from our player (`DropObject` with no drop menu open: a weapon rack or a mannequin in a player home, a mod placing the player's gear): the script keeps that reference, and taking it out of the world for a copy would leave the script holding a deleted one. Only a drop made from a drop menu (the inventory, or the console's `player.drop`) or by the developer channel is given.

**A drop.** The game's own event (`TESContainerChangedEvent`, from our player to nobody) names the reference the item became; it is our player's drop when a drop menu is open as it comes, or the developer channel made it (any other is a script's, above). It is watched until it comes to rest (still for half a second, no sooner than 1.5 s after the drop, or 5 s after it wherever it is), and reported where it lies (`kReportDrop`, with a random number of our game's own, its nonce). The server offers it back to its dropper alone (`kDropPlaced` with a drop ID): our game takes its own item out of its world (disabled at once, as the offer is heard, so our player can't pick it up after the copy is promised; deleted a second later: `src/game/Retire.h`), records that it did, says so (`kClaimDrop kPlaced`), and shows the session's copy in its place. Only then does the drop lie there for the others (`kDropPlaced` to every game), so nobody can take an item that is still in its dropper's world. An offer whose item our player picked up again first is answered `kKept`, and never lies anywhere. A report the server does not take (past the player's budget: 32 at once, then 4 a second; past the session's 1024 drops or a player's 256; an item or a place the session can't name) is answered with no drop ID: the item stays its dropper's own.

**The copies.** Each game shows a copy of every drop lying in the session while its player is in the same place (the same interior cell, or the same worldspace) within 5000 units, and removes it past 7000 or elsewhere. A copy is placed with the item's extras where the dropper saw it come to rest, and blocked from activation: our player's Take on it is a claim (`kClaimDrop kTake`, one per item until answered, 8 at most at once, again after 5 s unanswered). The server grants a drop to the first player who claims it while it lies there, and tells everyone (`kDropGone` naming the taker): every other game removes its copy; the taker's game picks its copy up as its player's own take, and checks that the copy left the world and that its player's count of the item rose. A pick-up that does not take is tried again every half second, 4 times; then the drop goes back to the session (`kGiveBack`). A later claim is answered with who has it. A game lacking a form of the drop places no copy, but still knows it lies there.

**Saves.** No copy is ever saved: each is taken out of the world before a save (named in the co-save, so a load of that save removes any it kept) and placed again after. What a save holds is the other half. Each game keeps a record of each session's drops ("SKDR" in the plugin's co-save, up to 8 sessions by the server's run id from the welcome, 4096 entries each): the drops whose item left its world (by nonce) and the drops it took in (by drop ID). After every welcome and every load the game sends it (`kDropRecord`, 4 then one in 2 s; past that the newest is owed, never dropped), and the server makes its book agree with that world: what the world holds (a drop it took, or its own that never left it) is that player's and lies nowhere; what the book had them hold but the world lacks lies there again. Then it sends the game every drop lying there (`kDropList`, in packets of 64; the drops a list lacks are removed here). So a save from before a drop has the item again and the drop goes from the session; a save from before a take lacks the item and the drop lies there again. The one case left is an item two worlds hold, as when a friend took a drop and its dropper loads a save from before dropping it: both keep it (counted in the server's log).

**Leaving.** A player who leaves takes their drops still lying there with them: the server withdraws each for everyone, and their game gives each back to its world as it leaves the session (where it lay when its player is near, else at their feet), with the drops the server had not confirmed yet. Each one given back is taken off the record of the session it left in (by then the record is bound to no session), only once it is in the world again, so a rejoin or a save made after leaving does not say it is still out, which would have the server lay it down again; the game also sends no record while items are still going back. The server keeps no file of its own, and the host's game is the server, so a drop lying there when the session ends would otherwise be in no world.

DropSync's state is under one lock, taken by the tick and by SKSE's callbacks on the main thread (the co-save, a save, a load); the event sinks never take it.

**Not yet:**
- The rig drops through the developer channel; a drop from the inventory menu itself (the drop menu the rule above relies on) is not driven by the rig yet.
- An item a plugin placed in the world, picked up: each game's own (above). Shared pickups of placed items need the pickup itself shared.
- A potion a player brewed, an enchantment a player made: runtime forms, not given.
- The server keeps no file: drops do not outlive the session, and a record is keyed by the server's run, not by a character (the sister project keys it by character and keeps a session file).
- A taker who leaves while a take is being finished: the server counts it as theirs.
- In an exterior, a copy is placed in our player's cell and moved to where the item lies, which may be a neighbouring cell (no save holds it, so only its cell's unloading is concerned: it is placed again).

## Quests

Since protocol 7 (runs and aliases since protocol 12). Not tested in a game yet; the rig steps `quests` and `jobs` are ready for it. The rules, free of the game, are `src/game/QuestRules.h`; the game side is `src/game/QuestSync`; the server's book is `common/QuestBook.h`; tests in `tests/QuestTests.cpp`.

The aim is that every quest is shared: a stage done is done for everyone, whoever did the step, and the host's save keeps it. This version shares a quest's stages, its objectives and its end (completed or failed); a conversation is seen and heard by the others near ("Conversations"). A reward a conversation gives is given to everyone ("Rewards", since protocol 23); scenes and quest items are each player's own for now (below).

**Which quests, by class.** Each quest is judged by its own record, never by a name list alone, so a mod's quest is shared as the base game's are and the load order does not matter:

| Class | How it is told | Shared? |
| --- | --- | --- |
| Shared | a journal tab (main quest, College, Thieves Guild, Dark Brotherhood, Companions, Daedric, side, Civil War, Dawnguard, Dragonborn), an editor ID, and not a radiant job | yes: stages, objectives, end |
| Own | a typed quest each player plays for themselves: the Helgen opening (`MQ101`), marriage, adoption (`QuestRules::OWN_QUESTS`) | no |
| Radiant | started by the Story Manager for an event, and not "run once": each game would pick its own job (its targets come from the event) | while the host's game runs it: the host's run, with the host's targets ("Runs and aliases"); a job a friend starts on its own is that friend's |
| Misc | the misc tab (favours, small errands) | no, in this version: a scan of which play the same everywhere comes first |
| Untyped | no journal tab: the game's machinery (dialogue, followers, trackers, encounters) | no |
| No name | no editor ID: nothing to name it by when it is made here | no |

Every game judges again by its own record before it makes anything, so a quest one game shares and another does not (another version of a mod) is made only where it is shared.

**What a game reports.** A stage done is read from the game's own event (`TESQuestStageEvent`; the sink only queues). Objectives and ends are read once a second from the shared quests that run; an objective is said with the quest's current stage in that game, the stage its shown part holds at. Each is reported when it is ahead of the session's word; a report counts as out until the server answers it, so a poll does not send it again. What the server would not take (refused: the quest ended the other way first; or its book full) stays this game's own and is not offered again unless it moves on; what it had already is learnt as the session's.

**A game's own past is never the session's.** When the session's word is new to a game (its welcome, the host's reset, its own load), what the game holds then is its base: its objectives and ends are not reported, only what moves on from them. So a friend that joins with a save ahead of the host's, or whose host loads an older save, does not push its own past into the host's world (stages are reported only from their events, which a load does not fire). A quest further on in a friend's game than in the session (the friend is at a stage the session has not reached, five seconds after the base, once the session's word has come) is apart: its stages, objectives and end there are the friend's own until the session reaches that stage, after which it is with the session again (`quests`: `apart=`, `apartStages=`). The host's game is never apart: its world is the session's.

**The server's book** (`common/QuestBook.h`) keeps the session's word on each quest, up to 4096 quests and 512 entries each. It only grows: a stage once done stays done; an objective goes forward only (the first end said, completed or failed, stays; shown stays shown, at the latest stage of its quest it was read shown at); a quest ends once, the first way said. News goes to every game, the reporter's too, with who said it; the rest goes back to the reporter alone with why (it had it, past the player's budget, full, refused). Each player has a burst of 64 batches and 8 a second after that (past it, answered busy: the game reports it again two seconds later), and two asks for every word and one in 5 seconds after that (owed, never dropped).

**The host's save is the world.** At its welcome and after each load the host's game says its world: `kQuestReset` (the server empties the book and tells the others), then a snapshot of its shared quests that run or that it has ended (completed or failed, stopped): their stages done, objectives and ends (since protocol 18 its own message, `kQuestWorld`, a burst of up to 1024 batches). The server passes the snapshot on to the others as the session's word (player 0), as it sends the book to a joiner: it is the world's past, not play, so a stage of it that moves the player is not made anywhere ("Stages that move the player"). A friend's reset or world is ignored. The reset is a line no quest word crosses (since protocol 20): the server comes back to the host with its reset after every word it passed on before it, and the host's game makes no other player's word heard between its load and that answer (`beforeReset=`); each other game says when it heard the reset (`kQuestResetSeen`, `resetsSeen=`), and the server drops that game's quest reports until then (sent from the old world and in flight). At the reset a friend's game drops its own reports still out and those it was to send again after a busy answer (`reportsDropped=`): they were of the world before, an entry left out would take the answer to a later report on the same thing, and one sent again would cross the line. If the server never comes back with the host's reset (10 seconds), the host's game warns and makes the others' words again (`echoMissed=`). A game that joins is sent the whole book after its welcome; a friend that loads a save asks for it again. A friend's own save holds its own quests as they were; the session's word is made where it is behind, never undone where it is ahead (forward only).

**Quests the host's world ended.** A friend whose save is behind on a quest the host finished (started it, not at the end) is caught up to its end, as for a quest that runs. A friend that never started it is not walked through every quest the host ever finished, one after another, at a join: the session's past on it is put aside (`QuestRules::Verdict::kParked`, counted `parked=`, held `parkedNow=`) until the quest starts in that game (its own play, or a stage made there starts it), and is then made in the order heard (`unparked=`), ahead of anything said of it since. A word said live (a friend finishing a quest during the session) is made as ever. The past comes in batches, a quest's end after its stages, so a quest not started in a game is not begun from the past until no word of it has come for 3 seconds (`QuestRules::PAST_SETTLE`): its end is known by then. "Started" here means one thing to every rule (`QuestRules::Here::Ran`): the quest runs, has ended, or was stopped part way (it has a current stage); a quest stopped part way is not put aside, and its stages below where it stopped are never set again. An ended quest is said in the host's world only when the host's game trusts the done bit ("Reading the stages"): its stages are read by that bit alone, and without it only its last stage would be said, setting a friend behind in it straight to its end (`snapshotEnded=`; the log says when they are left out).

**Runs and aliases.** Since protocol 12; the rig step `jobs` is ready for it. The rules, free of the game, are `src/game/QuestRunRules.h`; the server's book is `common/QuestRuns.h`; tests in `tests/QuestRunTests.cpp`. A quest's aliases (the people, places and things it is about) are filled by each game when the quest starts, and two games pick differently: a radiant job's target, the bandit camp a bounty names, the courier's letter. So the quest is the session's only when its aliases hold the same references and locations everywhere, and the host's game picks them:
- The host's game says each shared quest and radiant job it starts (its event, `TESQuestStartStopEvent`) as a run: a number its game never gives twice in its session, said fresh for a radiant job (its earlier run's stages are not this run's: the server and every game forget that quest's word). It reads the references its reference aliases hold and the locations its location aliases hold once a second while the quest runs, and says them when first read, whenever they change, and again every 30 seconds while unchanged (a word the server's budget dropped is not lost). A radiant job's stop ends its run: the stop is held a second after its event, so the job's last stages (that frame's, and one the engine reports just after the stop) are said first, then its end as the quest holds it (its objectives, completed or failed: the poll reads only quests that run), then the stop. The server never takes a stop ahead of the stages of the run it ends. At its welcome and after each load it says the runs of its world before its snapshot.
- The server keeps the host's word only (a friend's runs are its own picks, never passed on): the live runs and their references, sent to a game that joins or asks again before the quests' stages, so a quest is started with the host's references before its stages are made. A stage of a radiant job's run that ended is refused, so a friend's late word cannot start it again. The host's reset and a new session clear it.
- A friend's game holds the run's stages until the quest is started for it (`QuestRules::Verdict::kHold`). A quest not running there is started with the host's references: each reference alias's record is made a forced fill of the host's reference for the start, and each location alias's a forced fill of the host's location (one the host left empty and the record calls optional, a forced fill of none; one this game lacks, or one not loaded here, this game's own pick, counted), the engine's own start runs (as the Story Manager starts a job), and the records are put back once the quest runs, after 10 seconds, or before a load (records are the game's data, never saved). A quest already running there is taken as the run (adopted), so a rejoin or a friend that started the same job is lined up. Either way, a reference the host's alias holds and this game's does not is forced into the alias every 2 seconds while it differs (a reference not loaded yet is tried again). A quest whose start would leave an alias that only the Story Manager's event fills (a bounty's hold, a guild job's place) without the host's word is not started at all (`cannotStart=`): the engine would refuse it; it waits for the host's next word. A run whose references or start do not come within 10 seconds is given up: its stages are then made as before (this game's own picks), and a start the engine refused is tried again 30 seconds later. Given up is not the end: the host's later word starts it, and a quest that runs after all is taken as the run, the stages that were held or dropped made again from the session's word. A radiant job taken as the run whose location aliases hold other locations than the host's (a location is given only at a start) is stopped and started again once, with the host's; a shared quest's are said once in the log (`locApart=`). Each forcing, reference not loaded and location apart is logged once per run and alias. The host's stop of a radiant job stops it there, after its last word: the stages and end the session said of the run are made first (one thing every 250 ms, as always; a job whose last stage stops it there ends on its own), then `stopquest`, and only then is the session's word on it forgotten. What still waits after 20 seconds (held for a far friend, stuck) does not keep the job running. A new run of the job heard while the earlier one still ends there stops the earlier one first and starts the new one. A friend starts at most one quest for a run every 250 ms, the oldest heard first: one that joins a long game hears every run at once, and each start runs the quest's alias fills, its start-up stage and its scripts. A quest that stays starting there on its own start is given up after 10 seconds like the rest.
- A radiant job is shared only while it runs as the host's run. One a friend's game starts on its own stays that friend's job: its stages are not reported and the host's game never runs it.
- A radiant job a friend's game started or took for a run goes on running when the session's runs are no longer its word: the host loads a save from before the job (it died mid-bounty) or comes in again, the friend loads a save it made while the job ran for a run, or the session ends. Those jobs are kept: the friend's game remembers them across the host's reset, its co-save names the ones running for a run as it saves, and a session's end keeps them (a friend playing on alone keeps its jobs). Once it is a friend in a session again and the session's runs have had 10 seconds to come, each one no run claims is stopped there (`orphansStopped=`): it ran for a run the host's world does not have. A shared quest is never stopped (forward only), a job the friend stopped or started on its own since is its own, and a game that becomes the host keeps its world's jobs.
- Not shared: an actor a quest creates for its alias (a reference the host's game made as it ran: each game's own until NPCs are paired), a reference or location of a plugin a game lacks (that game's own pick), and every location alias while the game cannot read and write them.
- **Locations.** A location alias's location is not in CommonLibSSE-NG's layout, so each game finds it: the quest's map of alias to location (`TESQuest`, 0xA0, as in Fallout 4's engine) is read only under the quest's alias lock, and a value is used only when it is one of the load order's locations (never followed otherwise; counted `locUnread=`). Each game checks the map against the forced locations of running quests (at least 5, 4 in 5 held) before it says any (`quests`: `locMap=`). The slot of a location alias's record that keeps its forced location is found at load, by every forced location alias of the load order naming a location in the same slot and no other (`locSlot=`); without it a friend keeps its own locations. Neither is tried in a game yet: the rig step `jobs` checks both.

**Making the session's word here.** Each thing the session says is judged against this game: it has it already, the quest is missing (a mod this game lacks) or not shared here, a stage is below the quest's current stage here, running, ended or stopped without ending (passed: this game went past it, done or a branch it did not take, so it is never set again and its fragment never runs twice, whatever the done bit reads), an objective or end is of a quest not started here (its stages bring it, or were not made), the session's past is on a quest the session ended that this game never started (put aside, above), anything else of a quest this game stopped part way without ending it (another branch, or its own stop: stopped, counted `stopped=`, as `setstage` would start it again), or it is to be made. It is made by the game's own console commands (`setstage`, `SetObjectiveDisplayed`, `SetObjectiveCompleted`, `CompleteQuest`), so the quest's own scripts run here as they ran where the step was done:
- one thing every 250 ms, never a frame's worth;
- one stage of a quest at a time, in the order heard (a stage's fragment may set the next one itself), the next once the last reads done, or after 5 seconds (counted stuck, and the quest goes on);
- a quest's objectives and end only once its stages are made and 5 seconds have passed since the last one, as its fragments set most of them: whatever is still behind is then made directly. An objective's end is made whatever stage the quest is at here; its shown part only while the quest here is at the stage it was read shown at, because a later stage's own script may have withdrawn it (`SetObjectiveDisplayed(n, false)`), and did so here too: a withdrawn objective is never shown again from an older word;
- a failed end is counted, not made (the console has no command for it).

**Stages that move the player.** A stage whose fragment moves the player (a summons, "come with me"), or takes their screen, controls or saving away, would pull every friend across the map or leave them frozen or blind far from the scene that gives it back. `QuestRules::STAGE_RULES` names such stages, to be made only when the friend who did the step was near (from the session's past, a join or a load, not at all), and stages that are each game's own. Its rows (`src/game/StageRows.h`) are written by `tools/questscan.ps1 -Write`, a read-only scan of the game's own files (the quests of Skyrim.esm, Update.esm and the three add-ons, as the game loads them, and the compiled scripts in Skyrim - Misc.bsa): every stage of a typed quest whose fragment moves the player (MoveTo and its kin, SetPosition, TranslateTo, a door it makes them use, FastTravel), takes their screen and leaves it so (FadeOutGame, an image space that stays on, a race menu), their controls (DisablePlayerControls taking anything, SetPlayerAIDriven), freezes them (SetRestrained, SetDontMove, EnableAI off) or stops saving and waiting (SetInChargen), with an argument known only at run time counted as taking; itself or through what it calls (the quest's own script, any script a property or local is typed with, a few calls deep, a branch on a literal argument followed one way), the stages it sets and the start-up stages of the quests it starts. The player is a variable got from `Game.GetPlayer`, a property of the quest that holds the player's form (0x14), or, where the form is not known, one named for the player. Each row says what it does (`StageEffect`), the worst one found when a fragment does several, for the log. A row on a quest's start-up stage is marked so: any stage made while that quest is not started here starts it, and the engine runs the start-up stage too, so such a stage is judged by the start-up row as well. The scan does not see a scene's, a package's or a magic effect's own scripts, nor a reference reached through a variable set at run time; every stage the session's word made here that moved our player within 3 seconds (a change of space or a jump of 4096 units) is still said once in the log and counted (`quests`: `moved=`), so the rig and players' reports name the rows it missed. An image space that stays on is one cross-faded in, or applied or popped to when its record (IMAD) does not play a few seconds and end, or is not known (a variable set at run time, a property of a script on a reference); one that plays out by itself (a blur, a flash) is not a row, nor a fade or an image space the same code takes off again further on with no branch between (the Greybeards' word fade, white for two seconds). Taken off only past a branch, in a loop waiting on the player (Molag Bal's haunting) or by a later stage (the time freeze of the Psijic vision, the time travel of the Elder Scroll), it stays a hold. `-Dump <editor ID>` prints a quest's record and its fragments, disassembled, with what each image space property does, to check a row by hand; given an image space's editor ID it says what that one does.

*Near when it happened.* A row's stage has moved its doer by the time its word is read in another game (the fragment runs in the frame the stage is set), so nearness is taken as the word comes, not when the stage is made: each game reads, every frame, which friends are within 4096 units of our player in the same space, and a friend read near within 5 seconds before their word came was near at the step. Those near are made the stage and go along. A friend who was not near holds the stage (said once in the log, with what the stage does: `farHeld=`), and the quest's later stages wait behind it; it is made if they come near the doer, and given up (not made, the later stages go on) when the doer leaves the session or after 60 seconds (`farLeft=`, `farWaited=`, each in the log). So no friend is stuck behind a stage they were never near, at the cost of that stage's fragment: a row that fires too often costs a far friend a stage, a missing one a frozen friend.

**Reading the stages.** Whether a stage is done is bit 0 of the stage's flags as the engine holds them. That is read from the engine, not documented, so each game checks it at load against what it must be (no quest never run has a stage done; at least 9 in 10 running quests read their current stage done) and logs the verdict (`quests`: `doneBit=`). When it is not trusted, a stage counts as done only when it was seen set in this game or is the quest's current stage, and the host's snapshot says its current stages and the ones seen.

**Threads.** The console commands run from the plugin's tick, which until the frame hook is written runs on SKSE's task queue; each one run off the main thread is counted (`offmain=`), and each the game made no script to run in (`norun=`). The console runs a command it cannot compile without a word, so what is made is read again two seconds later: an objective or end that does not read so is counted and logged (`unmade=`), and a stage that never reads done is counted stuck.

**Not yet:**
- A conversation is the talker's: the others near see and hear it ("Conversations") and see the stage it set. Scenes play in each game for itself.
- Quest items are the world's they are in: one the quest holds in an alias comes as a reference, not as a reward, so whoever holds it hands it in (the quest's stages then follow for everyone). A reward given here is not given back if a friend loads a save from before it: it was a conversation of the session, not of that save.
- Misc quests are each game's own, and so is a radiant job a friend's game starts on its own (only the host's jobs are the session's).
- An actor a quest creates for its alias is each game's own until NPCs are paired, and so is a quest's location alias in a game that cannot find where the engine keeps it (`locSlot=none` or `locMap` not verified). Such a location is not read there, so it is neither the same as the host's nor apart from it (`unread=` in `quests run`): it never restarts a radiant job, is never said apart, and the run's references are judged on their own (`refSame=`).
- A choice a quest keeps in a script variable rather than a stage (which side a player took in a dialogue) is not shared.
- A quest a friend took further in its own save than the host has (apart) stays the friend's own until the host reaches that stage; the friend cannot hand it to the host.

## Conversations

Since protocol 15. Not tested in a game yet; the rig step `talk` is ready for it. The rules, free of the game, are `src/game/TalkRules.h` (with `src/game/SubtitleTime.h` and `src/game/LineSounds.h`, ported from the sister project); the server's book is `common/TalkBook.h`; the game side is `src/game/Conversations`; tests in `tests/TalkTests.cpp` and `tests/LineSoundsTests.cpp`.

One player talks with an NPC, and the others near see it and hear it: the NPC's lines in their subtitle area over the NPC, with the NPC's own recording played from the NPC, and the talker's chosen topics over the talker's stand-in. The conversation itself (its menu, its choices, what it sets in a quest) stays the talker's; the others watch it, as players stand around a friend who talks with someone. A stage it sets is shared as every quest stage is ("Quests").

**What is a line, by class.** Each line is read from what the game shows, never from a list of topics, so a mod's dialogue is shared as the base game's is:
- every line the NPC our player talks with says while the Dialogue Menu is open with it: its subtitle as the game shows it (`HighProcessData::voiceSubtitle`), so a line with a variable filled in (a name, a sum of gold) is the text our player read. Each new subtitle is a line; the same text again within 300 ms is the same line (the game sets it more than once). The game keeps a speaker's last subtitle after the line ends, so when a talk begins (or a session is joined, or a save loaded, mid-talk) the subtitle already up is held back (`primed=`), not sent: its goodbye or ambient line of before is no line of this talk; a greeting with the very same words still goes, since the game says it begins it (its topic event). Its recording is found from the topic info being said (the response whose text it is: the NPC's greeting, or a copy of the topic our player picked, made while the menu is open under the menu's own lock and only once that topic is found in the menu's lists, never read from the engine after the menu closed), and sent as its path under `Sound\Voice\`, which every game with the same plugins has; one the rules do not trust (no `Sound\Voice\` root, `..`, another extension than `.fuz`, `.xwm` or `.wav`) is sent without one, the line shown and not heard;
- the topic our player picks: its text, said by the talker's stand-in, with no recording (the player character has no voice);
- the end of a line said early (the talker skipped it, or left): the others' recording of it ends too, unless it would end within 750 ms anyway. An end is the line's own only when it is of the same topic info (an earlier info's end, fired late once the next line is up, cuts nothing: `endsOther=`).
A line is sent with the speaker as a form the other games share (`FormTranslate`: a placed NPC of a plugin both have); a speaker made at run time (a summoned or spawned actor, an NPC a quest created) is sent as none, and the others show the line as a notice with the speaker's name. Lines and their names are cut at a character boundary (1024 bytes of text, 128 of name) and lose control characters.

**How it is shown.** In each game that hears the line:
- far (more than 1400 units from both the speaker and the talker's stand-in, or no speaker in this world): nothing, counted `far=`;
- when the game's own settings would show a nearby NPC's line (general subtitles on, and our player in no conversation of their own: the game then shows that conversation's lines alone, so a friend's line is a notice): in the subtitle area over the speaker, the game's own subtitle list, for as long as the game shows a line of its length (`SubtitleTime`). The game owns that list, so after 200 ms each game checks the line is still there; one it dropped is shown as a notice instead, and after three such drops the session shows notices only (`subsOff=1`);
- otherwise as a notice: "{speaker}: {line}", in the player's language.
The same line from the same speaker again within 5 seconds is shown once (`repeats=`), and no more than three lines of one speaker in one talk are shown in 3 seconds (`tooMany=`): two conversations near a player, and a talker's own topics, each have a budget of their own.

**How it is heard.** The recording is played from the speaker (followed as it moves) as a 3D sound through the game's dialogue output model, never through the dialogue system, which would start the NPC's own talk in that game. It is found in that game's data (`.fuz`, then `.xwm`, then `.wav`, loose or in an archive); one not there is counted `missing=`, one the audio manager will not play `unplayed=`. Each sound has a hard end: its own length, or the subtitle's time when that cannot be read. At most one line of a speaker plays at a time: a new one ends the last (`cutCrowded=`), and one still playing past its end is ended (`cutLong=`).

**One talker at a time.** Two players talking with one NPC at once would each lead it through a different conversation. A game says whom its player talks with (`kTalk`, on when the menu opens with an NPC, again every 5 seconds, off 2 seconds after it closes so a goodbye still said is kept), and the server's book (`common/TalkBook.h`) gives each placed NPC to one player: the first to ask, until they say off, leave, or go 20 seconds without saying it again. A player who talks with another NPC within those 2 seconds keeps the one before until their game says it off, so its goodbye still passes (one before at most: an older one is over). A player told another talks with that NPC (`kTalkAnswer`) has its menu shut and is told so ("{name} is talking with {player}."), when its player started the talk; a forcegreet (the NPC walked up and spoke) is left to run, its lines kept in that game (`busyRefused=`), as shutting it would start it again. Lines from a player who does not hold the talk are dropped by the server. An NPC made at run time is never in the book: each game's own. The book holds 64 talks; past that a talk is let through and not kept. The server passes on a player's lines in a burst of 16, then 4 a second.

**Threads.** The topic event (`TESTopicInfoEvent`) only queues; the conversation is read, and friends' lines shown and played, from the plugin's tick. The subtitle list is written under its own lock; each write off the main thread is counted (`offmain=`).

**Not yet:**
- An NPC that talks to another NPC (a scene) is each game's own: each game plays it for itself, as the game does today, and a scene a quest starts plays in every game where its stage is set.
- A forcegreet in two games at once (both players near an NPC who walks up to speak) plays in both; the server lets the first through and the other game keeps its lines.
- Talking activators (a shrine, a skull that speaks) and the player's own shouts are not lines.
- Who talks with an NPC is not yet the NPC's sync: an NPC the talker's game moves as it talks (turning, a gesture) moves there only, until NPCs are synced.
- Read from the engine and checked on the rig: whether a line put in the game's subtitle list stays there (`talk subs`, `dropped=`); the sound flags the voice plays with; that the game keeps a speaker's last subtitle up (`primed=`); that the topic picked is in the menu's lists while it is said (`topicUnlisted=`); and that `isGreetingPlayer` is set for an NPC's forcegreet only, never for the greeting of a talk our player began (else every busy talk is kept open: `busyRefused=` in place of `busyClosed=`).

## The menu
